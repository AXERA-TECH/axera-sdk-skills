# Platform: m57

Axera M57 架构层 Secure Boot 事实与路径。所有指令基于 M57 家族芯片的 BootROM、
SBL、SPL、U-Boot 代码路径与镜像格式；AX637/AX637R 的 board 层特化见叠加的
`<SKILL_ROOT>/platforms/ax637.md`。

## 目标平台配置与公共构建规则

确认用户给出的 `PLAT` 后，才定位对应配置文件：

```
build/platforms/axera/<PLAT>/config.mk
```

关键变量及组合约束在 M57/AX637 SDK 中共用：

| 配置 | 作用 | 约束 |
|---|---|---|
| `SECURE_BOOT` | 编译安全启动代码并生成/打包签名镜像 | 加密和 dm-verity 的前提 |
| `ENABLE_CIPHER` | 生成并选用密文签名启动镜像 | 需先启 `SECURE_BOOT`；设备需正确配置 Root Key/FEK |
| `SIGN_USE_RSA3072` | `TRUE`=RSA-3072；`FALSE`=RSA-2048 | 密钥、DTS 公钥和镜像算法必须一致 |
| `SIGN_USE_RSA_PSS` | `TRUE`=后段镜像用 RSA-PSS 填充；`FALSE`=RSA-PKCS#1-v1.5 | SBL 恒用 PKCS#1-v1.5（BootROM 兼容）；此位只影响 SBL 之后的 SPL/ATF/OP-TEE/U-Boot/Kernel 的 FIT 签名填充，切换会影响后段验签 |
| `ROOTFS_DMVERITY` | 生成并选用 `rootfs_signed.img` | 需先启 `SECURE_BOOT`；仅允许 EXT4/SQUASH |
| `ROOTFS_FS_TYPE` | `EXT4` / `SQUASH` / `UBI` | dm-verity 只允许 `EXT4` 或 `SQUASH` |

构建前读取目标 `config.mk` 的 `check_combination`；至少拒绝
`SECURE_BOOT=FALSE` 与 `ENABLE_CIPHER`/`ROOTFS_DMVERITY`，以及 `UBI` 与
`ROOTFS_DMVERITY` 的组合。不要把 NAND UBI 平台擅自改成 dm-verity。

SDK 的构建入口在 `build/Makefile`。从 SDK 根目录完整构建可用
`make -C build PLAT=<PLAT>`；已有组件镜像的 AXP 打包目标为
`make -C build PLAT=<PLAT> axp`。仅展示 AXP 构建计划的命令为
`make -C build PLAT=<PLAT> axp -n`（或 `--dry-run`）。用户只要求命令说明、
或当前为不含 Makefile/工具链的精简样本时，只给出命令，不执行。

## 公共构建产物与 Download / AXDL 安全

| 组件 | 非 Secure Boot | 签名 | 加密并签名 |
|---|---|---|---|
| SBL | `sbl_signed.img`¹ | `sbl_signed.img` | `sbl_enc_signed.img` |
| AutoSAR/RTOS | `Mcal_Demo_signed.img`¹ | `Mcal_Demo_signed.img` | `Mcal_Demo_enc_signed.img` |
| SPL | `u-boot-spl_signed.img`¹ | `u-boot-spl_signed.img` | `u-boot-spl_enc_signed.img` |
| U-Boot | `u-boot.img` | `u-boot_signed.img` | `u-boot_enc_signed.img` |
| ATF | `bl31.img` | `bl31_signed.img` | `bl31_enc_signed.img` |
| OP-TEE | `optee.img` | `optee_signed.img` | `optee_enc_signed.img` |
| Kernel | `kernel.img` | `kernel_signed.img` | `kernel_enc_signed.img` |
| rootfs | `rootfs.img` | `rootfs.img` 或 `rootfs_signed.img` | 不加密；dm-verity 仍用 `rootfs_signed.img` |

¹ 基础产物名带 `_signed` 不代表已启用签名链，仍以配置和镜像 header 为准。
`build/scripts/axp_make.sh` 在 `SECURE_BOOT=TRUE` 时选择签名镜像，
`ENABLE_CIPHER=TRUE` 切换到 `*_enc_signed.img`，`ROOTFS_DMVERITY=TRUE` 选择
`rootfs_signed.img`。

只有 eFuse Secure Boot 已使能时，BootROM 才强制校验 FDL 签名；安全 FDL 名称为
`fdl1_signed.img`、`fdl2_signed.img`，FDL 只签名不加密。Download 禁用位与 FDL
验签是两类独立控制。

## 公共 eFuse 规划要点

- Root Key 必须先于依赖项写入，写入后 CPU 不可读回；FEK 仅在固件加密时需要，且不可跨芯片复用。
- M57/AX637 预留多个 PKH 区域；量产前按《AX EFUSE 使用说明》和产品规划选择区域、轮换策略与锁定位。
- eFuse 写入不可逆。先完成未烧写 eFuse 的软件签名链、恢复路径和篡改测试，再进入显式确认的量产烧写。

## 信任链

| 当前阶段 | 校验的下一级对象 | 主要机制 |
|---|---|---|
| BootROM | SBL | SBL 固定 header、SHA-256、RSA 签名；eFuse Secure Boot 使能后还校验 header 公钥的 PKH |
| SBL | SPL、AutoSAR/RTOS | 镜像 header、SHA-256、RSA 签名 |
| SPL | ATF、OP-TEE、U-Boot | U-Boot FIT 签名校验（SHA-256 + RSA） |
| U-Boot | Kernel、rootfs root hash | Kernel FIT 签名；rootfs root hash RSA 签名 |
| Linux | rootfs 数据块 | dm-verity hash tree 按需校验 |

## RSA 密钥文件对照

只读咨询生成/替换 RSA 密钥和同步 DTB 公钥时，本节已给出密钥路径、格式、命令及 DTS 节点。
按“离线生成密钥 → 导出 PKCS#1 公钥 → 替换下表文件 → 用 `extract_pkey_param.py` 提取参数并更新对应 DTS 节点 → 重新构建 SPL/U-Boot”说明步骤。
提取脚本输出参数，仍须将参数写入 DTS；不要将运行提取脚本本身视为已同步。
源码缺失时注明 DTS/脚本尚未在当前工作区核验，给出实际 SDK 中的检查步骤并完成答复。


| 算法 | 私钥 | 公钥 | U-Boot DTS 节点 |
|---|---|---|---|
| RSA-2048 | `tools/imgsign/private.pem` | `tools/imgsign/public.pem` | `key-akcipher2048` |
| RSA-3072 | `tools/imgsign/key_3072/private.pem` | `tools/imgsign/key_3072/pubkey.pem` | `key-akcipher3072` |

DTB 公钥节点位于 `boot/uboot/u-boot-2022.10/arch/arm/dts/m57-keys.dtsi`。
替换 PEM 后必须用 `python3 build/scripts/extract_pkey_param.py -k <pubkey>` 提取参数写入
对应节点。指南中出现的 `m57h-keys.dtsi` 与当前源码不一致，一律以 `m57-keys.dtsi` 为准。

### 密钥生成（在受控 Linux 服务器上离线进行）

公钥必须是 **PKCS#1 格式**（`-----BEGIN RSA PUBLIC KEY-----`），不能用默认的 SPKI 格式
（`-----BEGIN PUBLIC KEY-----`）；SDK 签名工具与 `sample_efuse_key` 均按 PKCS#1 解析。

```bash
# 生成 RSA 私钥（2048；3072 同理改位数）
openssl genrsa -out private.pem 2048
# 导出公钥 —— 必须加 -RSAPublicKey_out，得到 PKCS#1 格式
openssl rsa -in private.pem -pubout -RSAPublicKey_out -out public.pem
```

替换到上表路径后，用 `extract_pkey_param.py` 同步 DTB 公钥。私钥与 AES 材料永不入
源码 / 日志 / 工单。

### AES Key 生成（构建侧，需固件加密时）

`tools/imgsign/aes-256.key` 是**文本格式的 64 个 hex 字符**（对应 32-byte AES-256 Key），
`img_aes.py` 的 `get_aes_key()` 按 `binascii.unhexlify` 解析。生成命令：

```bash
openssl rand -hex 32 > tools/imgsign/aes-256.key
```

SDK 自带的 `aes-256.key` 为全 0 占位值，不可用于量产。设备侧烧写的 FEK 是
"Root Key 封装后的 AES Key"（40-byte），与构建侧明文 AES Key 必须配套，见 §公共 eFuse 规划要点。

## eFuse 烧写工具分工

烧写密钥与 bondoption 使用**两个不同工具**，不可混用：

| 工具 | 路径 | 职责 |
|---|---|---|
| `sample_efuse_key` | `msp/sample/efuse_key/` | 烧写 PKH（`pubkey`）、Root Key（`rootkey`）、FEK（`aeskey`）、HSM HUK（`hsmhuk`） |
| `sample_efuse` | `msp/sample/efuse/` | 读写任意 blk（`-r/-w/-l/-p`），用于烧写 bondoption（blk14/blk64 的 secure boot / pkh flag / encrypt 等配置位） |

要点：

- `sample_efuse_key` 源码 `efuse_key_tool.c` 中 `#define EFUSE_WRITE_ENABLE 0`；为 0 时
  `pubkey`/`rootkey`/`aeskey` 只计算打印、不写入。真正烧写需改 1 重新编译（`hsmhuk` 不受此宏控制）。
- `sample_efuse_key aeskey` 写死 `aeskey_static_array` 固定测试值（不可量产）；烧写自定义
  AES Key 需改源码，或走 U-Boot `ax_efuse_key aeskey <addr>`（`boot/uboot/u-boot-2022.10/cmd/ax_efuse_key.c`，
  从内存地址读取明文 32-byte AES Key 封装烧写）。
- 烧写 bondoption 用 `sample_efuse -w <blk> <data>`；其 `bondopt_check()` 会在写 blk14/blk64 前
  预检——将使能 secure boot 而对应 PKH 未烧写、或使能 encrypt firmware 而 FEK 未烧写时取消写入，
  防止砖化。
- 关键位：blk14(bondoption0) bit14=pkh flag0、bit15=rootkey protect；blk64(bondoption1)
  bit0=secure boot、bit1=encrypt firmware、bit2=pkh flag1。

烧写顺序：先 Root Key → 再 FEK（加密时）→ 烧 PKH → 最后使能 secure boot / encrypt 位。

命令接口速查（只读咨询中仅说明用法，实际烧写前仍须确认）：

| 用途 | 命令接口 | 条件 |
|---|---|---|
| Root Key | `sample_efuse_key rootkey random` | 写后不可读回；工具会自动使能 rootkey protect |
| FEK | `sample_efuse_key aeskey` | 默认是固定测试数组；自定义密钥按上文改源码或使用 `ax_efuse_key aeskey <addr>` |
| PKH | `sample_efuse_key pubkey <key_idx> <pubkey_pem_file>` | 按目标密钥槽选择索引，与签名公钥一致 |
| bondoption | `sample_efuse -w <blk> <data>` | 按实际已烧写状态计算位值，依赖项验证后最后使能 |

接口来源：`reference/m57/58 - AX EFUSE使用说明.md` 的密钥烧写章节；写入开关与工具限制见上文。

## 故障定位

### BootROM trace（`BS 0x... BN`）

BOOT 字段是 `BS` 后第 5 个 32-bit，SECURE 字段是第 9 个（`BS` 前缀本身不计数）。
按位或累积，非十进制错误码。

**BOOT_DEBUG_FLAG 关键位**：

| 掩码 | 标志 | 串口短码 | 含义 |
|---|---|---|---|
| `0x00000800` / `0x00001000` | `BOOT_READ_CE_FW_FAIL` / `BOOT_VERIFY_CE_FW_FAIL` | RF / CF | HSM/CE 固件读或 checksum 失败 |
| `0x00010000` | `BOOT_SECURE_INIT_FAIL` | SIF | HSM/CE 初始化失败 |
| `0x00020000` | `BOOT_VERIFY_PUBKEY_FAIL` | PKF | SBL header 公钥校验失败（结合 SECURE 字段区分 eFuse/hash/PKH） |
| `0x00040000` | `BOOT_CIPHER_SHA_FAIL` | SHF | SBL SHA-256 计算失败 |
| `0x00080000` | `BOOT_AES_DECRYPTO_FAIL` | DF | SBL 解密失败 |
| `0x00100000` | `BOOT_VERIFY_RSA_FAIL` | RSF | SBL RSA 签名验签失败 |
| `0x80000000` | `BOOT_READ_S_IMG_HEADER_FAIL` | R2F | 签名段 SBL header 读取失败 |

**SECURE_DEBUG_FLAG 关键位**（伴随 PKF 时看）：

| 掩码 | 标志 | 含义 |
|---|---|---|
| `0x2` | `SEC_DBG_EFUSE_INIT_FAIL` | eFuse 初始化失败 |
| `0x8` | `SEC_DBG_READ_KEY_HASH_FAIL` | 选中 PKH 读取失败 |
| `0x10` | `SEC_DBG_HASH_KEY_FAIL` | header 公钥 SHA-256 失败 |
| `0x20` | `SEC_DBG_KEY_VERIFY_FAIL` | header 公钥 hash 与选中 PKH 不匹配 |
| `0x40` | `SEC_DBG_KEY_VERIFY_PASS` | 本次公钥检查通过（不等于 eFuse 已使能） |

### DOWNLOAD trace（`DS 0x... DN`）

`DOWNLOAD_DEBUG_FLAG` 是 `DS` 后第 5 个 32-bit（完整 `BS ... BN` trace 中则是第 12 个）。
关键位：`DL_HANDSHAKE_OK(0x1)`、`DL_SEND_VER(0x2)`、`DL_CE_INIT_FAIL(0x4)`、
`DL_CE_WAIT_INIT_FAIL(0x8)`、`DL_VERI_HEAD_FAIL(0x10)`、`DL_PUB_KEY_VERI_FAIL(0x20)`、
`DL_SHA_FAIL(0x40)`、`DL_RSA_FAIL(0x80)`、`DL_SECURE_SUCC(0x100)`、`DL_OK(0x200)`、
`DL_EIP_READ_END(0x400)`、`DL_WAIT_CE_INIT(0x800)`。

### SBL 串口日志关键字（先找关键字，再看紧邻 `Secure boot: mark ...`）

| 关键字 | 失败点 | 首查 |
|---|---|---|
| `verify img header failed: header 0x...` | header/magic/checksum 或读取异常 | 分区、slot、启动介质 |
| `secure init failed(<ret>)` | HSM/CE 初始化失败 | HSM 固件与状态 |
| `secure aes decrypto failed(<ret>)` | 加密镜像解密失败 | 明/密文混刷、Root Key/FEK vs. AES Key |
| `secure public key verify failed(<ret>)` | header 公钥未过 PKH 校验 | eFuse PKH、RSA 位数、镜像来源密钥 |
| `secure cipher sha256 failed(<ret>)` | SHA-256 计算失败 | HSM、镜像完整性、存储稳定性 |
| `secure cipher rsa verify failed(<ret>)` | RSA 签名验签失败 | 私钥/公钥配套、RSA 位数、签名后是否被改写 |
| `Secure boot: mark spl slot:<n> partition as failed` | 失败对象为 SPL slot n | 对应 A/B slot 的 SPL 镜像 |
| `Secure boot: mark rtos slot:<n> partition as failed` | 失败对象为 RTOS slot n | 对应 A/B slot 的 RTOS 镜像 |

例如，`secure cipher rsa verify failed(-9)` 紧邻
`Secure boot: mark spl slot:0 partition as failed` 时，定位为 **SBL 对 SPL slot 0 的 RSA 签名验签失败**；
`-9` 是该调用返回码，不是 BootROM BOOT 字段位掩码。来源为 `SafetyIsland/sbl/boot/boot.c`：
`cipher_rsa_verify()` 返回负值后打印前一条日志并返回 `BOOT_RSA_FAIL`，后续失败标记给出镜像与 slot。
只凭这两条日志不能确定密钥不匹配、镜像损坏或具体损坏偏移；先核对签名密钥集合、RSA 位数与烧写镜像。
已有构建产物及只读导出镜像时，可用以下命令核对完整性（占位路径需按实际产物替换）：

```bash
sha256sum /path/to/built_spl_signed.img /path/to/spl_slot0_dump.img
cmp /path/to/built_spl_signed.img /path/to/spl_slot0_dump.img
```

精简路由样本没有这些源码或镜像时，直接说明上述日志含义与核对方法，列出待补充证据；不用反复搜索样本中不存在的实现。

### SPL/U-Boot 串口日志关键字（`board_pre_hang()` 写故障记录）

| 关键字 | 失败点 | 首查 |
|---|---|---|
| `## Checking hash(es) for config <name> ...` | 开始 FIT config 签名校验 | 单独出现不是失败，看后续 |
| `## Checking hash(es) for Image <name> ...` | 开始校验 `<name>` 的 FIT image | 根据 `<name>` 区分 ATF/OP-TEE/U-Boot |
| `Unable to verify required signature` | required 签名缺失或未过 | 私钥、`required` 节点、SPL DTB 公钥 |
| `Verification failed` | RSA 签名值校验失败 | 签名密钥、RSA 位数、DTB 公钥、签名后改写 |
| `Bad Data Hash` | FIT image/config hash 不匹配 | 镜像损坏、ITS/FIT 与最终包同源 |
| `## Decrypting Image <name> ... Error` | FIT 镜像解密失败 | 加密开关、Root Key/FEK、AES Key |
| `Operation not permitted` | 校验/解密返回 -EPERM/-EACCES | 结合先前签名/hash/decrypt 日志；故障类型 `FAULT_ILLEGAL_IMAGE` |
| `Misc fault: <ret>` | 未分类错误 | 保留返回值与更早的错误 |

### Kernel 串口日志关键字

| 关键字 | 失败点 | 首查 |
|---|---|---|
| `Unable to find extlinux on device (ret = <ret>).` | 未找到 extlinux 配置 | boot 分区/路径/slot/文件系统 |
| `Skipping <label> for failure retrieving kernel` | Kernel 文件读取失败 | extlinux 中 Kernel 路径、存储 |
| `Unable to verify required signature` / `Verification failed` | Kernel FIT 签名缺失/失败 | 加载的是否为签名 Kernel、U-Boot DTB 公钥 |
| `Bad Data Hash` | Kernel FIT 数据/配置 hash 不匹配 | Kernel 完整性、签名后替换、混包 |
| `Bad Linux ARM64 Image magic!` | 解包 Kernel magic/格式错 | 错文件、错地址、错格式 |
| `PXE boot failed with error: 1, hang up...` | Kernel/Initrd 加载或参数失败；`FAULT_LOAD_IMAGE` | 向前找 `Skipping ...` |
| `PXE boot failed with error: 2, hang up...` | 非法镜像/校验失败；`FAULT_ILLEGAL_IMAGE` | 向前找 `Verification failed`、`Bad Data Hash` |
| `PXE boot failed with error: <>, hang up...` | 初始化类失败；`FAULT_INIT_FAILURE` | 保留负返回值与早期日志 |

### 故障字段布局（`board_pre_hang()`）

| 字段 | 含义 |
|---|---|
| `fault_id[23:0]` | 错误类型（`FAULT_ILLEGAL_IMAGE=0x2`, `FAULT_LOAD_IMAGE`, `FAULT_INIT_FAILURE`） |
| `fault_id[31:24]` | 阶段（SPL/U-Boot/Kernel） |
| `fault_reason[23:0]` | 被校验镜像（ATF/OP-TEE/U-Boot/Kernel/rootfs） |
| `fault_reason[31:24]` | slot（0=A, 1=B） |
