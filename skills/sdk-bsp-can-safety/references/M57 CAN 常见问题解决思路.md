本文整理 CAN 开发和调试过程中常见的问题，分别从**问题场景**和**解决方案**两个方面说明排查重点及处理建议。

## [1. CAN Bus-Off]

### [1.1 问题场景]

CAN 节点在报文发送或接收过程中持续检测到通信错误，发送错误计数器达到协议规定的阈值255后，CAN 控制器会进入 **Bus-Off** 状态。进入该状态后，节点停止参与总线通信，表现为：

- 报文发送持续失败；
- 接收不到其他节点报文；
- CAN 控制器状态显示为 Bus-Off；
- 如果没有正确的恢复机制，节点可能长期无法恢复通信。

在 AUTOSAR 架构下，Bus-Off 的状态管理和恢复流程通常由 **CanSM（CAN State Manager）** 负责协调，涉及 CanIf、CAN 驱动以及上层通信状态管理。若 MCAL 层同时开启自动恢复，可能与 CanSM 的状态机控制产生冲突，导致状态管理不一致或恢复流程异常。

### [1.2 解决方案]

#### [AUTOSAR 环境]

- 由 **CanSM** 统一处理 Bus-Off 检测、状态切换和恢复流程；
- 在 MCAL/CAN 控制器配置中关闭硬件或驱动层的自动 Bus-Off 恢复功能，避免 MCAL 绕过 CanSM 自行恢复；
- 确认 Bus-Off 通知能够通过 CAN Driver、CanIf 正确上报至 CanSM；
- 检查 CanSM 的 Bus-Off 恢复策略、恢复等待时间和网络状态切换配置；
- 恢复后确认 CAN 控制器重新进入 Started 状态，并验证报文收发是否恢复正常。

#### [非 AUTOSAR 环境]

- 如果系统没有 CanSM 或其他上层状态管理模块，建议开启 CAN 控制器或 MCAL 提供的自动 Bus-Off 恢复功能；
- 若只能使用软件恢复，则应在 Bus-Off 错误回调中执行受控的停止、清除错误状态和重新启动流程；
- 同时排查导致 Bus-Off 的根因，例如物理层干扰、波特率或采样点不匹配、终端电阻异常以及报文配置错误，不能仅依赖自动恢复掩盖总线问题。

## [2. CAN 中断处理时间过长]

### [2.1 问题场景]

CAN ISR（Interrupt Service Routine）或 CAN 中断回调中加入了阻塞式打印、格式化输出、锁等待或其他耗时处理，导致中断服务时间过长。常见现象包括：

- 后续 CAN 中断不能及时响应，出现丢帧；
- 其他高优先级或实时性任务的响应延迟增大；
- 高总线负载下问题更加明显，低负载时不易复现。

特别是 `printf`、串口打印或日志框架通常可能涉及锁、缓冲区等待和字符逐个发送，不能假设其执行时间是固定且足够短的。

### [2.2 解决方案]

- 不要在 CAN ISR 或中断回调中加入阻塞式打印；
- ISR 中仅完成必要的硬件状态读取、FIFO/邮箱数据搬运、错误状态确认和事件通知；
- 将调试信息写入无锁环形缓冲区、RAM 事件队列或设置状态标志，由后台任务或低优先级线程异步输出；
- 避免在 ISR 中进行复杂协议解析、动态内存分配、长循环、锁等待或报文批量处理；

## [3. CAN TX 失败]

### [3.1 问题场景]

节点调用发送接口后，报文未能成功发送，可能表现为发送返回失败、发送确认超时、发送邮箱长期忙或 CAN 控制器不断产生错误。一个常见原因是总线上没有其他节点对发送报文返回 **ACK**。

CAN 的 ACK 位由其他正常接收该报文的节点产生，发送节点自身不会为自己的报文提供 ACK。因此，在仅连接一个节点、对端未上电、对端处于静默模式或对端无法正确采样报文时，发送节点可能因收不到 ACK 而不断重发，最终进入错误状态甚至 Bus-Off。

此外，收发节点的 CAN bit timing 不一致，也可能导致对端无法正确识别报文并返回 ACK。

CANFD 模式下，需要确定配置的CANFD ISO 模式，因为ISO 和NONE ISO 物理标准是不同的，无法通信。

### [3.2 解决方案]

- 确认总线上至少存在两个正常工作的 CAN 节点：发送节点和能够正确接收报文的对端节点；
- 确认CAN节点CANFD 的模式都是CAN ISO 模式，这个在EB 工具有单独的配置选项，因为ISO 和NONE ISO 物理标准是不同的
- 确认对端节点已上电、已初始化并处于正常通信模式，而不是 Silent、Listen-only 或 Bus-Off 状态；
- 检查两端的 nominal bit rate、采样点（Sample Point）、同步跳转宽度（SJW）以及 time quanta 配置是否匹配；
- 使用 CAN 分析仪或示波器检查总线波形、位时间和 ACK 位，区分“没有 ACK”和“有 ACK 但发生位/格式/CRC 错误”；
- 检查 CANH/CANL、GND、收发器供电、终端电阻和总线拓扑。总线两端通常应配置匹配的终端电阻，不能随意增加或缺失；
- 发送失败的同时应读取 CAN 控制器错误状态和错误计数器，确认是否由 ACK Error、Bit Error、Stuff Error、Form Error 或 CRC Error 引起。

## [4. CAN Rx 丢帧（RX Enhanced FIFO 溢出]
### [4.1 问题场景]

使用 **RX Enhanced FIFO** 接收报文时，如果报文到达速度超过FIFO 深度16，最终发生 overflow。发生溢出后，后续到达的报文可能无法写入 FIFO，从而表现为 CAN Rx 丢帧。

常见诱因包括：

- CAN 总线负载过高，报文到达过于密集；
- RX 中断优先级较低或响应不及时；
- 接收中断处理时间过长，尤其是在 ISR 中执行打印；
- CPU 长时间关闭中断或被其他高优先级任务占用，AUTOSAR OS 中有关闭总中断的接口，需要合理的使用

### [4.2 解决方案]

- 在 MCAL 的 RX Enhanced FIFO 配置中启用 overflow 错误回调函数；
- 在 overflow 错误回调中只执行轻量操作，例如递增 `rx_fifo_overflow_count` 错误计数器、记录时间戳或设置诊断标志；
- 不要在错误回调或 CAN ISR 中执行阻塞式打印，详细日志应由后台任务异步输出；
- 统计并监控 FIFO overflow 次数，以确认丢帧是否确实由 FIFO 溢出导致，而不是过滤规则、ID 配置、软件队列或上层处理逻辑造成；
- 提高接收处理及时性：合理设置 CAN 中断优先级，缩短 ISR 执行时间，并由任务及时批量读取 FIFO；
- 检查接收过滤器，避免不需要的报文进入 FIFO；
- 通过 CAN 分析仪记录总线实际报文数量，并与驱动接收计数、FIFO overflow 计数及上层收到的报文计数进行对比，定位丢帧发生在哪一层。
