# 诊断结论与原厂交接（Phase 5）

证据等级：**已确认异常**有本次直接证据；**高可信待验证**有支持证据但仍缺指定实验；**信息不足**表示关键材料缺失或冲突。处理状态另按主流程记录，确认异常不等于已解决。

## 报告模板

默认使用以下四节，以完整传达判断和下一步为准，不为凑字数扩写。多轮对照、证据冲突或原厂交接时，按需要展开相关部分。

- 每个事实只说明一次，保留所有会影响结论或下一步的证据。目标设备、轮次和关键环境随证据注明，未知项集中放在末节。
- 完整 proc、音频哈希、逐窗统计和执行记录保存在原始材料或 measurements 中，正文引用位置，仅列支持判断的指标。
- 多轮或分段问题用一张小表对照关键变化：参考输入是否有效、重启前后及启动/恢复段、削顶与音量/增益对照、单讲与双讲差异。共用条件只写一次，保留会改变处理步骤的候选原因，并为每项给出区分实验。
- 对照表随行标注出处；正文措施每项一短段，写清动作、预期与关键回退。结构化交付时，完整候选和逐项反证、回退细节放 diagnosis.json，正文引用即可。
- 已确认配置异常时，先给修正和复测步骤；其他链路排查作为“修正后仍异常”的下一步。时差只有影响本次判断或措施时才展开。
- JSON 中每个 observation/action 字段只写该字段需要的信息，不重复背景段落；相同证据在正文引用 JSON 定位，反证、回退及未知边界仍须保留。
- 回归判据每项一句；全部未执行时统一说明原因。结构化交付保留契约要求的字段，JSON 和正文引用同一证据、措施和状态。

```markdown
## 结论与证据
<一句话原因、证据等级、故障方向及问题归属；事实与推断分开>
处理状态：待补证据 / 待复测 / 已解决
<目标设备/轮次、复现条件；关键配置、返回值及录音观察，每项附文件:行号或音频区间>
<必要的对照、冲突及判断边界>

## 处理步骤
<按优先顺序列修改/补采动作，结合证据说明理由、预期、反证和回退；涉及采集时注明上限及恢复>

## 复测结果
<远端单讲、近端单讲、双讲、静音、原触发条件>
<每项判据、通过/失败/未执行及证据；音量相关问题保留目标播放音量和近端拾音要求>

## 缺项与下一步
<影响当前修正或验收的缺项及采法；修正后仍异常时最关键的验证>
<需交接时附最小复现、已排除项、原厂待确认事项及临时措施的限制>
```

“已解决”须有本次修正后满足客户标准及上述全部回归通过的证据；输出全零、脚本成功或一次未复现不能替代复测。

结构化交付按 [contract.md](contract.md)，优先写 diagnosis.json 后调用 render_report.py 自动生成并校验 Markdown。普通非结构化答复仍可直接使用上面的四节模板。
