# Linux 与 QNX 平台差异

**什么时候读**：S1 判定平台时；客户搞混了平台；客户手上有另一平台的资料想套用；你有一边的经验想迁移结论时。

M57 上 Linux 和 QNX 的 **Safety 软硬件是同一套**——FCU、ECM 的硬件工作原理和工作状态完全一致，错误码表逐字节相同。但**软件实现和运行时接口差异极大**，直接套用会给出错误结论。

## 一句话总结

| 层次 | 是否相同 |
|---|---|
| Safety 硬件（FCU/ECM 芯片行为） | **完全相同** |
| 错误码表、mask 位域、MID/domain 枚举 | **完全相同**（逐行相同） |
| SafetyIsland 侧代码 | **基本相同**（实测 `Fcu.c` 仅差 1 行 fault 表项） |
| 心跳阈值、去抖轮次 | **相同**（都是 5ms 单轮、`> 5` 上报） |
| **诊断框架的特权级** | **完全不同**（EL1 内核态 vs EL0 用户态） |
| **主域通信机制** | **完全不同**（真 netlink vs QNX 消息传递） |
| 主域软件实现、运行时接口 | **完全不同** |

所以：**mask 解码结果可以互通，排查命令、代码路径、通信机制、调试手段不能互通。**

## 判断当前是哪个平台

```bash
test -d "<SDK>/kernel/linux/linux-6.1.83/drivers/soc/axera/fusa" && echo LINUX
test -f "<SDK>/kernel/osdrv/private_drv/diag_core/driver/diag_stl.c" && echo QNX
```

辅助判据：

| 判据 | Linux | QNX |
|---|---|---|
| `build/version/m57_version.mk` | `SDK_VERSION=V2.10.0`（无前缀） | `QNX_V1.10.0` |
| manifest 文件名 | `M57_SDK_V*.xml` | `M57_SDK_QNX_V*.xml` |
| SDK 文档名 | `docs/internal/domain/bsp/diagcore.md` | `fusa_diagcore.md` |
| 板端节点根 | `/sys/devices/platform/axdiag/` | `/proc/ax_diag/` |

**不要**用「有没有 `code_review/`、`fcu_codereview/` 目录」当判据——那是个人 review 工作区产物，不在 manifest 里，随时可能出现或消失。

## 差异一：诊断框架的特权级（EL1 vs EL0）

<EXTREMELY-IMPORTANT>
**Linux 的诊断框架是内核态（EL1）驱动；QNX 的诊断框架是用户态（EL0）resmgr 进程。**

QNX 的代码虽然放在 `kernel/osdrv/private_drv/` 路径下，**但那只是目录命名沿用，与实际特权级无关**。不要因为路径里有 `kernel` 就当成内核驱动来排查。
</EXTREMELY-IMPORTANT>

### 证据

| | Linux | QNX |
|---|---|---|
| 构建体系 | Kbuild（`obj-$(CONFIG_AXERA_DIAG_CORE) += diag-core.o`） | QNX `qtargets.mk`（`common.mk:49`） |
| 产物名 | `diag-core.ko` / built-in | `NAME := diag_core_drv`（`common.mk:8`） |
| 安装位置 | 内核镜像 / `/lib/modules` | `INSTALLDIR=usr/bin`（`common.mk:36`）→ **`/usr/bin/diag_core_drv`** |
| 文件类型 | ELF 内核模块 | `ELF 64-bit LSB shared object, interpreter /usr/lib/ldqnx-64.so.2`（标准用户态 PIE） |
| 入口 | `platform_driver_register()`（`diag_core.c:1398`）、`MODULE_LICENSE`（`:1403`） | `int main()`（`diag_core.c:2042`）、`daemonize()`（`:2058`） |
| 特权获取 | 天然全部内核权限 | `ThreadCtl(_NTO_TCTL_IO, NULL)`（`diag_core.c:2051`）+ `mmap_device_memory` |
| 服务注册 | platform device + sysfs | `resmgr_attach()`（`diag_core.c:2002`）、`dispatch_create_channel()`（`:1982`） |
| 启动方式 | 内核 probe / insmod | IFS 启动脚本当命令执行（`kernel/qnx/configs/m57-demo.build:82-85`） |

### QNX 是四个独立进程，不是一个框架

`m57-demo.build:82-85,159` 启动的是四个独立可执行程序：

| 进程 | 职责 |
|---|---|
| `diag_core_drv` | 诊断框架核心 |
| `diag_extend` | 扩展模块（`/dev/diag_extend`） |
| `m57_ecm_drv` | ECM 驱动 |
| `fcu_drv` | FCU 驱动 |

**任一进程挂掉，其余三个仍在跑，但功能残缺。** Linux 侧不存在这种失效模式——所有代码在同一个内核地址空间，一起活一起死。

<EXTREMELY-IMPORTANT>
**这条有安全含义，排查时必须重视**：QNX 的 `diag_core_drv` 崩溃退出后，系统照常运行，但**诊断能力已静默丢失——故障不再上报**，且不容易被发现。Linux 侧内核 Oops 通常连带整机不可用，反而更容易被察觉。

所以客户报「以前有诊断日志，最近没有了」时，QNX 侧**第一件事是确认四个进程还在不在**，不要当成「没有故障所以没日志」。
</EXTREMELY-IMPORTANT>

### 对排查手段的影响

| 手段 | Linux（EL1） | QNX（EL0） |
|---|---|---|
| 附加调试器 | 只能 kgdb/crash，量产板基本做不到 | 可 `gdb attach` / `pdebug` 到 PID，能单步、看变量 |
| 崩溃现场 | Call trace / Oops / panic，只有内核栈回溯 | 进程 core dump（dumper），完整用户栈，事后 `gdb core` 分析 |
| 崩溃影响面 | 内核 Oops 通常整机不可用 | 单进程退出，系统继续跑，**诊断能力静默丢失** |
| 日志去哪 | `dmesg` / printk ratelimit | **进程 stdout**（见下方警告） |
| 卡死诊断 | RCU stall、soft lockup、hung task detector 自动打印 | `pidin -p <进程名>` 看线程阻塞态（REPLY-blocked / RECEIVE-blocked / MUTEX） |
| 进程重启 | 需 rmmod/insmod，实际几乎不做 | 进程重启即状态清零，`name_attach` 重建，但已注册 handle / 心跳配置全丢，MSP 侧需重连 |
| 观测接口 | sysfs + debugfs | resmgr 挂的 `/dev/...` 路径 |

<EXTREMELY-IMPORTANT>
**QNX 的 diag 日志不走 slog2。** `include/diag_log.h:124-128` 的 `diag_printf()` 内部是 `printf()`/`vprintf()`，日志去了进程的标准输出（daemonize 后取决于重定向）。

虽然 `slogger2` 在系统里跑（`m57-demo.build:29`），但 diag 框架本身没接 `slogf`。**告诉客户「用 slog2info 看诊断日志」是错的**，会让客户找不到日志然后以为框架没跑。
</EXTREMELY-IMPORTANT>

### 一个需要打折扣的地方

**「QNX 诊断全在 EL0」在讨论中断延迟和实时性时不成立。** QNX 的 ECM/FCU 中断入口仍在微内核，`libax_ecmirq`（`ecm/lib/common.mk:8` 的 `NAME := ax_ecmirq`）只是 `InterruptAttach` 的用户态壳。真正的中断响应路径还是内核态。

所以：讨论**调试手段、崩溃影响、进程生命周期**时按 EL0 理解；讨论**中断延迟、实时性**时不能简单说「都在用户态所以慢」。

## 差异二：netlink 的真假

<EXTREMELY-IMPORTANT>
**Linux 侧的 netlink 是真正的内核 netlink socket；QNX 侧的「netlink」只是沿用了这个名字，实际是 QNX message passing（`name_attach` + `MsgSend`/`MsgReceive`/pulse），与网络协议栈毫无关系。**

这是最容易误导客户的一条。客户看到 "netlink" 会去 `dmesg | grep netlink`、查 `/proc/net/netlink`、抓包、怀疑网络配置——**在 QNX 上这些全是死路**。
</EXTREMELY-IMPORTANT>

### 证据

| 用途 | Linux | QNX |
|---|---|---|
| 头文件 | `<net/sock.h>`、`<linux/netlink.h>`（`diag_netlink.c:15-16`） | `<sys/dispatch.h>`、`<sys/netmgr.h>`（`diag_netlink.c:18-19`），**无 socket 头** |
| 建立服务 | `netlink_kernel_create(&init_net, NETLINK_SOC_DIAG, &cfg)`（`:207`） | `name_attach(NULL, DIAG_NETLINK_DRIVER_NAME, 0)`（`:386`） |
| 协议号/名字 | `NETLINK_SOC_DIAG 23`（`include/uapi/linux/diag_netlink.h:18`） | 字符串 `"diag_core_drv"`（`include/diag_netlink.h:24`） |
| 连接对端 | portid（`NETLINK_CB(skb).portid`，`:95`） | `name_open(DIAG_NETLINK_SAMPLE_NAME, 0)`（`:165`） |
| 报文构造 | `nlmsg_new`（`:142`）、`nlmsg_put`（`:146`）、`nlmsg_data`（`:152`） | 无，直接传结构体 |
| 发送 | `netlink_unicast(sk, nl_skb, portid, MSG_DONTWAIT)`（`:159`） | `MsgSend`（`:229`、`:235`） |
| 接收 | netlink input 回调 | `MsgReceive`（`:282`）、`MsgReply`（`:304`） |
| 断连感知 | `NETLINK_URELEASE` notifier（`:33`、`:212`） | `_PULSE_CODE_DISCONNECT` pulse（`:292`）→ `ConnectDetach` |
| 用户态 | `socket(AF_NETLINK, SOCK_RAW, NETLINK_SOC_DIAG)`（`netlink_monitor.cpp:321`） | `name_attach`/`name_open`（`netlink_monitor.cpp:392`、`:400`） |

### grep 陷阱

<EXTREMELY-IMPORTANT>
在 QNX 侧 `rg 'NETLINK_'` **会有命中**，但全部是宏名前缀的**假阳性**：

- `DIAG_NETLINK_EXIT_PULSE`（`include/diag_netlink.h:43`，定义为 `_PULSE_CODE_MINAVAIL + 1`）
- `DIAG_NETLINK_DRIVER_NAME`、`DIAG_NETLINK_SAMPLE_NAME`

**不要**据此认为 QNX 侧有 netlink。判断真假 netlink 要搜 `netlink_kernel_create`、`nlmsg_`、`AF_NETLINK`——这些在 QNX 侧命中数为 0。
</EXTREMELY-IMPORTANT>

### 结构与失败模式的差异

**连接结构**：Linux 是标准的内核 socket / 用户态 client。QNX 是**双向双通道**——driver 和 app 各自 `name_attach` 一个自己的通道，再互相 `name_open` 对方的名字，不是单一 client/server。

**同步性**（对排查影响最大）：

| | Linux | QNX |
|---|---|---|
| 发送语义 | `MSG_DONTWAIT` 异步非阻塞 | `MsgSend` **同步阻塞** |
| 缓冲满/对端慢 | 直接 `-EAGAIN`/`-ENOBUFS`，**静默丢消息**，用户态无感 | 一直卡在 SEND/REPLY-blocked，**反向拖住 driver 的发送线程** |
| 排查着眼点 | 有没有丢消息、用户态有没有及时收 | 线程有没有阻塞、对端有没有 `MsgReply` |

QNX 侧 `diag_netlink.c:229-241` 那段「失败 → `close_peer` → 重新 `name_open` → 重发一次」的逻辑就是为应对这个问题存在的。app 名字没起来时，driver 每次发送都要试一次 `name_open` 并打 warn 日志——这正是 QNX「diag-netlink 错误刷屏」类问题的来源。

**抓包能力**：

- **Linux**：是真 socket，理论上可用 `ss -f netlink`、`nlmon` 虚拟接口 + tcpdump 抓。协议号 23 是自定义的，通用工具解不了 payload，但至少能看到 portid、报文长度、丢包。
- **QNX**：**一个包都抓不到**，没有网络栈参与。只能用 `pidin`（看线程 REPLY/RECEIVE 阻塞态）、`traceprinter`/`tracelogger` 抓内核事件里的 MsgSend/MsgReceive。

## 运行时接口

<EXTREMELY-IMPORTANT>
这一节是最容易踩的坑。QNX 的排查命令在 Linux 上**全部无效**，反之亦然。
</EXTREMELY-IMPORTANT>

| 项 | Linux | QNX |
|---|---|---|
| 根路径 | `/sys/devices/platform/axdiag/` | `/proc/ax_diag/` |
| 层级命名 | **数字**：`domain0/module0/error17/` | 当前 SDK 也使用 `domain0/module0/error17/`；历史名字示例以现场 `ls` 为准 |
| 全局控制 | `/sys/class/fusa/diag/diag/` | 当前 SDK 在 `/proc/ax_diag/` 根导出全局属性 |
| 注入参数 | `/sys/kernel/debug/diag_fault_inject/` | 无（走命令行工具 `diag_tools`） |
| 注入总开关 | `inject_enable`（**有**，不开则注入全被门控挡掉） | 当前 SDK 有 `/proc/ax_diag/inject_enable`，工具 `-i` 会尝试打开 |
| `cycle_enable` 层级 | **两级**（domain 级 + module 级都要开） | 当前 SDK 的 BSP domain0 与 module 两级都要检查，其它域以实际注册为准 |
| domain 开机自检 | `d_boot_error`（有 `d_` 前缀） | 当前 SDK BSP domain0 为 `d_boot_error`，module 为 `boot_error` |
| `/dev/ecm`、`/dev/fcu` | **不存在**（纯 platform device + sysfs） | 存在（resmgr 设备节点） |
| ECM/FCU 查询 | sysfs 属性 | `ecm_fault` / `fcu_fault` 工具 |
| ECM/FCU 注入 | 写 `fault<N>/inject` | `ecm_fault` / `fcu_fault` 工具 |
| 诊断工具 | `diag_tools`（shell 脚本，**两个版本行为不同**） | `diag_tools`（ksh 脚本） |
| 进程查看 | `ps aux` | `pidin ar` |
| CPU 负载 | `top -bn1` | `hogs -n -%1` |
| 内存 | `free -m`、`/proc/meminfo` | `pidin info`、`df -h /tmp` |
| 日志 | `dmesg` | 串口 / 进程 stdout |

**Linux 有完整 ECM/FCU sysfs，QNX 只有命令行工具**——这是 Linux 在排查上的优势，能直接读到每个通道的 `happed_num`、`mask`、`status`。

## 架构差异

### 域的层数

- **QNX 三域**：Safety Island R 核（mcal）↔ 用户态 diag server（msp）↔ diag_core（**用户态 resmgr 进程**）
- **Linux 四域**：SafetyIsland ↔ kernel diagcore ↔ 用户态 AxDiagCore ↔ 客户 app，比 QNX 多一层用户态服务的明确边界

### FCU 实现方式

<EXTREMELY-IMPORTANT>
**Linux 的 FCU 是纯转发（`axera,fcu_virt`），不直接操作硬件寄存器**；所有请求经 RPMsg 转发给 SafetyIsland 执行。当前 QNX SDK 的 `fcu_drv` 硬件控制/状态查询也经 RPMSG 转发，部分查询有约 1 秒的条件等待，本地统计可直接返回（`private_drv/fcu/driver/fcu.c:506-546,629-681`）。

后果（Linux 特有）：

1. FCU 同步读取可能不可中断地无限等待，`timeout` 不能保证结束 → **已有读取卡住或通信状态不明时，先取现有任务栈与 RPMsg/握手日志，不新增同步读取**；无响应不能单独证明未建链
2. 并发读 `fault0/*` 和 FCU 级属性会互相抢 completion，返回值可能串台 → **必须串行访问**

QNX 不能套用上述 Linux 等待机制，也不能据此排除自己的 RPMSG/并发问题；先串行查询，异常时检查现有阻塞态和通信日志。查询中的约 1 秒等待不是整个工具调用的退出保证。QNX 侧的 `fcu_register_callback()` 注册/注销成对、mask/eoi/unmask 序列那一套排查清单，在 Linux 侧不适用——Linux 没有对应的用户态回调库。
</EXTREMELY-IMPORTANT>

### ECM/FCU 用户态库

| | Linux | QNX |
|---|---|---|
| 用户态库 | **无** | `libax_fcuirq`、`libax_ecmirq`、`fcu_api.c`、`fcu_callback.c` |

QNX 那套「注册成功 ≠ 立即能收事件」「注册/注销必须成对」的排查要点在 Linux 侧没有对应物。

### 编译开关

| | Linux | QNX |
|---|---|---|
| 机制 | Kconfig | Makefile 宏 |
| 例子 | `CONFIG_AXERA_ECM_STL` | `USE_ECM_STL` |
| 总开关 | `CONFIG_AXERA_FUSA_SUPPORT` | `SUPPORT_AX_DIAG` |
| 怎么查 | **`.config`**（不是 defconfig，很多符号靠 `select` 带出） | Makefile / build 脚本 |

### 补丁检索范围

| | Linux | QNX |
|---|---|---|
| review 目录 | **实测不存在**（`fcu_codereview/`、`code_review/`、`doc_modify/` 三个都没有，也不在 manifest 里） | **存在且必须搜**——补丁可能在 review 中而非主线 |

QNX 侧有实测案例：某条 FAQ 说 V1.1.0 修了 FCU `set_mask` 竞态，但主线 `private_drv/fcu` 下搜不到关中断原语，补丁躺在 `fcu_codereview/239461d.diff`。

## 相同的部分（可以放心互通）

**心跳机制**：单轮阈值 `SERVER_HEARTBEAT_TIMEOUT = 5`ms，累计 `> 5` 轮才报 `heartbeat timeout`。两边实现一致，`heartbeat time:N` 的解释也一致。

**mask 位域**：`(domain << 27) | ((module & 0x7FF) << 16) | event`。逐字节相同。

**错误码表**：739 行、620 条目，逐字节相同。所以在一个平台上查到的符号名在另一平台同样有效。

**domain / MID 枚举**：逐行相同（仅版权头注释不同）。domain 16 = `MCAL_CDD`、MID 17~26 = ECM 区间，两边一致。

**SafetyIsland 侧**：基本相同（实测 `Fcu.c` 仅差 1 行 fault 表项）。所以 SafetyIsland 相关的资料和结论大体可以借用——这是两平台唯一能直接互通的代码部分。

**配置生成链路**：都是 Excel → `make PLAT=<平台> fusa_config` → 生成 JSON/头文件。改了 Excel 必须重跑，两边一样。

## 原语对照（读另一平台资料时的换算）

FAQ 或文档里的描述若来自另一个平台，按这张表换算再去 grep：

| Linux | QNX |
|---|---|
| `local_irq_save` / `spin_lock_irqsave` | `InterruptLock` / `InterruptDisable` |
| `spin_lock` / `mutex_lock` | `pthread_mutex_lock` |
| `wait_for_completion_timeout` | `MsgReceivePulse` + `TimerTimeout` |
| `msecs_to_jiffies` | `nsec` 直接计算 |
| `pr_info` / `dev_err` | `printf`（**非 slogf**，见上方警告） |
| platform device + sysfs | resmgr + `/dev` 节点 |
| netlink socket | `name_attach` + `MsgSend`/`MsgReceive` |
| `module_init` / `platform_driver_register` | `main()` + `resmgr_attach` |

**搜不到对应原语时不能判定「未含修复」**——可能只是换了实现方式。

## 客户跨平台时的提醒

客户从一个平台迁到另一个平台时，最容易出错的五件事：

1. **照抄排查命令** → 路径和节点名全不同，会得到「节点不存在」的假结论
2. **照抄配置改法** → Linux 是 Kconfig + sysfs，QNX 是 Makefile 宏 + `/proc`
3. **以为 FCU 行为一致** → 两侧当前实现均涉及 RPMSG，但等待与回复处理不同，须分别核对，不能互套超时或并发结论
4. **以为 netlink 是同一个东西** → QNX 侧是消息传递，抓包、`/proc/net/netlink` 全无意义
5. **以为诊断框架都在内核** → QNX 侧是用户态进程，进程崩溃后诊断静默失效，调试手段也完全不同

而 mask 解码、错误码含义、心跳语义可以直接沿用，不用重新学。
