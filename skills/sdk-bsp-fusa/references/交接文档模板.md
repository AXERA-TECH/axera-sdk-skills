# 交接文档模板

**S6 用。** 三轮无果或定性为疑似新缺陷时产出。

模板主体两平台通用，**标注「平台补充」的段落按判定结果二选一**。

## 目标读者

两类人，都要照顾到：

- **原厂工程师** — 要能快速判断归属域、优先级，以及「这个我见过/没见过」
- **AI（原厂侧的 AI 助手）** — 要能直接接手继续排查，不用把客户问过的话再问一遍

所以事实要结构化、可检索，推理链要显式写出来，附件路径要能对上。

## 目录结构

```
fusa-handoff-<YYYYMMDD>-<关键词>/
├── README.md                      主交接文档
└── attachments/
    ├── original-log.txt           客户提供的原始日志（完整，不截断）
    ├── evidence-round1.txt        S4 第一轮命令与输出
    ├── evidence-round2.txt        第二轮
    ├── evidence-round3.txt        第三轮
    ├── config-snapshot/           相关配置文件快照
    │   ├── <诊断配置 json>
    │   ├── m57_version.mk
    │   └── kernel-dot-config-fusa.txt   （仅 Linux：.config 里 FuSa 相关行）
    └── suggested-patch.diff       若有建议补丁（未落盘）
```

`<关键词>` 用归属定位得到的符号名简写，如 `isp-pipe-frame-id`、`fcu-handler-timeout`、`ecm-stl-init-fail`。

命令输出**原样保存**到附件，不要在 README 里粘贴长输出——README 里只放结论和关键片段，指向附件行号。

## 写作要求

**平台必须写在最显眼处。** README 标题下第三行就要标平台，第 0 节写判定依据。否则原厂拿到文档还要再问一遍，或按错误平台去查——两平台的路径和命令零重合，方向一错整轮白费。

**事实与推测严格分开。** 每条陈述要么有出处（FAQ 条目号、`文件:行号`、附件里的命令输出），要么明确标注「推测」「待验证」。第 7 节的「不确定的环节」是必填项，不要为了显得确定而省略。

**已排除项要写排除依据。** 只写「已排除心跳问题」没用，要写「已排除心跳问题：归属定位得 mask `0x002D0011` = ISP_PIPE 帧 ID 校验，与 module 0 的心跳无关；且 `number` 为 0」。

**保留客户原话。** 现象描述用客户自己的表达，不要改写成「专业」说法——客户的措辞本身可能含有线索。

**长输出进附件。** README 里的日志摘录不超过 5 行，其余指向附件。原厂 AI 会去读附件。

**FAQ 编号照抄原文。** 两个平台的 FAQ 编号格式不同且会持续新增，引用时直接写该平台 FAQ 文件里的原始编号，不要换算或跨平台映射。

**时间线是 Linux 侧的必填项。** 原厂看 Linux FuSa 问题的第一个动作就是找最早的原始故障——`cyclework overdue`、heartbeat、`FCU_HANDLER_TIMEOUT` 大多是下游症状。把时间线整理好能省掉一轮往返。

**Linux 侧不要声称查过 Jira/Gerrit。** 本 skill 是纯离线自助流程。QNX 侧可以引用 FAQ 的版本速查附录，因为那是 FAQ 自带的知识，不是查询结果。

## 交付说明

文档写完后告诉客户：

1. 目录位置
2. 怎么打包：`tar czf fusa-handoff-<YYYYMMDD>-<关键词>.tar.gz fusa-handoff-<YYYYMMDD>-<关键词>/`
3. 发给原厂时附上什么话（引用 README 第 9 节），并注明产品名与平台
4. 提醒检查附件里是否有不宜外发的内容（客户自己的业务代码片段、内部路径等）

最后一条要主动提，客户可能没意识到日志里带了自己的业务信息。
