# 归属定位（公共部分）

**S2 必读。这一步不能跳过。**

读完本文后，再读平台补充：`归属定位-linux.md` 或 `归属定位-qnx.md`。

不做归属定位就直接套 FAQ 的 err 号速查表，会把 ISP 问题误判成心跳问题——因为 FAQ 里的 err 号速查表隐含 `module 0` 前提，而这个前提往往没写出来。

<EXTREMELY-IMPORTANT>
本文的内容**两个平台完全通用**：mask 位域、错误码表内容、domain 枚举、module 全表逐字节相同。

只有**错误码表的文件路径**和**符号名前缀**按平台不同，见平台补充文件。
</EXTREMELY-IMPORTANT>

## 三步定位法

### ① 拿到 mask

两种日志形态，都要能解：

| 形态 | 样子 | 解法 |
|---|---|---|
| **A · 直接给 mask** | `error_mask: 0x002D001D` | 直接按位域拆三段 |
| **B · 给三元组** | `err ID: 29 module ID: 45 domain ID: 0` | 先合成再查表 |

合成公式（**两平台相同**）：

```
mask = (domain << 27) | ((module & 0x7FF) << 16) | event
```

反向拆解：

```
domain = mask >> 27
module = (mask >> 16) & 0x7FF
event  = mask & 0xFFFF
```

命令行算法：

```bash
# 合成：domain=0 module=45 event=29
printf "0x%08X\n" $(( (0<<27) | ((45 & 0x7FF)<<16) | 29 ))

# 拆解
M=0x002D001D; echo "domain=$(( M>>27 )) module=$(( (M>>16) & 0x7FF )) event=$(( M & 0xFFFF ))"
```

### ② 查表得确切符号名

在对应平台的错误码表里搜这个 mask：

```bash
rg -n "0x002D001D" "<错误码表路径>"
```

错误码表路径按平台不同（见平台补充文件），但**内容逐字节相同**（739 行、620 条目）。所以在一个平台查到的符号名在另一平台同样有效。

**必须查表，不要凭 module 号猜。** 这张表是权威来源。

查不到时的排查顺序：

1. 确认 domain 是否算错（domain 16 是 `MCAL_CDD`，不是 `MAIN_BSP`）
2. 用 `rg "0x00<MM>"` 列出该 module 全部条目，看邻近值
3. 检查该模块是否在当前配置下未编译

### ③ 判定归属，选排查路线

| 符号名特征 | 归属 | 排查路线 |
|---|---|---|
| `*_DFC_*`（module 0） | 诊断框架自身 | FAQ 的 err 号速查在此**才**成立 |
| `*_ECM_*` / `*_ECM_SAFETY_*` | ECM 就地检测层 | 读 `<SDK>/docs/internal/domain/bsp/ecm.md` + 平台 ECM 清单 |
| `*_FCU_SAFETY_*` | FCU 跨域汇聚层 | 读 `<SDK>/docs/internal/domain/bsp/fcu.md` + 平台 FCU 清单 |
| 其它具体子系统 | 该子系统自检 | 查自检实现，**并同时走 ECM/FCU 双层检查** |

符号名前缀按平台略有不同（QNX 有 `AX_` 前缀），见平台补充文件。

## 为什么 module 号决定一切

实测对比，同一个 `err 17`：

| 日志三元组 | mask | 符号名 | 含义 |
|---|---|---|---|
| `err 17 module 0 domain 0` | `0x00000011` | `*_DFC_DIAG_SERVER_HEARTBEAT` | server 心跳超时 |
| `err 17 module 45 domain 0` | `0x002D0011` | `*_ISP_PIPE_ISP_PIPE_FRAME_ID_CHECK` | ISP 帧 ID 校验失败 |

两者毫无关系。若照「err 17 = server 心跳超时」去处理 module 45 的日志，会让客户白查 CPU 负载。

**相邻日志只能帮助还原时间线，不能替代 ID 解码。**

## Domain 枚举

**两平台逐行相同**（仅版权头注释不同）：

| ID | 名称 | 说明 |
|---|---|---|
| 0 | `MAIN_BSP` | 主域 BSP，模块最多 |
| 1 | `MAIN_SYSTEM` | 主域系统（diag_server） |
| 2 | `MAIN_PLATFORM` | 主域平台 |
| 3 | `MAIN_ADAS` | 主域 ADAS |
| 4 | `SAFETY_BSP` | 安全域 BSP |
| 16 | `MCAL_CDD` | 安全岛 MCAL/CDD |

**domain 16 是常见陷阱**——它是 `MCAL_CDD`（安全岛），不是主域。算错 domain 会查不到表。

出处：Linux `include/linux/diag_enum.h:12-19`；QNX `ax_diag_type_ex.h:638-643`。

## ECM 与 FCU 的两级关系

```
硬件 ECC/校验错误
      ↓
  ECM 就地检测        ← 挂在各子系统旁，映射该子系统 ECM 寄存器
      ↓ (FAULT_A / FAULT_B IRQ)
  FCU 跨域汇聚        ← 全芯片故障事件总线
      ↓
  Safety Island R5F
      ↓
  上报到诊断框架 / 用户态
```

<EXTREMELY-IMPORTANT>
**ECM 是 FCU 的上游。** ECM 驱动启动时会为自己的 FAULT_A / FAULT_B IRQ 注册 FCU 回调——ECM 检测到的错误是**经 FCU 上报**的。

所以一个 ECM 类故障码，两层都要查：ECM 侧看检测是否误判，FCU 侧看上报链路是否正常。反过来，一个 FCU 故障也可能根源在某个 ECM 子系统。
</EXTREMELY-IMPORTANT>

ECM 错误分 correctable / uncorrectable 两类，对应 FAULT_A / FAULT_B 两条 IRQ 线。

## 子系统故障的双层检查

归属定位到具体子系统（如 ISP_PIPE、IVE、EMMC、NPU）时，除了查该模块自检实现，还要：

1. 确认该子系统是否有对应 ECM 控制器（看 module 17~26 区间是否有相关项）
2. 若有，走该平台的 ECM 排查清单
3. 确认上报是否经 FCU——若是，走该平台的 FCU 排查清单
4. **只有排除 ECM/FCU 两层后**，才认定问题在子系统自身

平台各自的 ECM/FCU 排查清单条目差异很大（Linux 6+6 条、QNX 8+8 条，仅 FCU handler timeout 一条重合），见平台补充文件。
