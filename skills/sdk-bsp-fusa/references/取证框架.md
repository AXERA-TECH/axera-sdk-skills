# 取证框架（公共）

**S4 用。** 生成命令让客户在板子上执行并回填。

本文是**两平台通用的方法**。实际命令见 `取证命令-linux.md` 或 `取证命令-qnx.md`，属性含义见 `运行时接口-<平台>.md`。

## 使用原则

- 一次给 6~8 条，不要更多。先给必做项，看回填结果再追加按需项。
- **每条都要说明看什么、什么值算正常。** 客户不知道 `cycle_enable` 该是 0 还是 1。
- 命令要能直接复制粘贴，别让客户自己拼路径。
- 客户回填后逐条比对预期，把「符合预期」的项排除掉，缩小范围。
- 全部只读，除了客户明确同意的开关类操作。

## 路径确认永远是第一条

<EXTREMELY-IMPORTANT>
**先让客户列出实际节点，不要凭 FAQ 示例路径硬猜。**

哪些模块存在取决于编译配置与设备树，FAQ 里的示例路径不一定在客户板子上成立。硬猜的后果是客户回一句「没有这个文件」，白跑一轮。
</EXTREMELY-IMPORTANT>

两平台的第一条命令都是「列出节点结构」，只是路径不同（Linux `/sys/devices/platform/axdiag/`，QNX `/proc/ax_diag/`）。

## 症状分支目录

两平台共用同一套分支划分，命令体不同：

| 分支 | 触发关键词 | 两平台都有？ |
|---|---|---|
| 1. 心跳类 | `heartbeat`、心跳超时 | ✅ |
| 2. 周期自检类 | `cyclework`/`cyclecheck`、`cycle`、overdue | ✅ |
| 3. 注入类 | 「注入没生效」、`diag_tools -i` 没反应 | ✅ |
| 4. 配置不生效类 | 改了 Excel/JSON 没反应 | ✅（Linux 更细） |
| 5. ECM 类 | module 17~26、`ECM_*` 符号名 | ✅ |
| 6. FCU 类 | `FCU_SAFETY`、`FCU_HANDLER_TIMEOUT`、`0x800A0010` | ✅ |
| 7. 压测/稳定性类 | 长稳、高负载、卡死、Call trace、RCU stall | ✅ |
| 8. 编译/开关类 | 「关了开关还在」、「改了配置不生效」 | ✅ |

## 通用判据

这几条判定逻辑**两平台一致**，只是读取路径不同：

### `number` 才是「真的上报了」的证据

日志在刷但 `number` 为 0，说明还在去抖过程中，**没有正式上报故障**。这是区分「设计预期的过程日志」和「真故障」的关键判据，心跳类问题尤其依赖它。

| `number` | `heartbeat time:` 日志 | 结论 |
|---|---|---|
| 0 | 有，在刷 | 去抖过程，未真正上报 → 设计预期 |
| > 0 | 有 | 真的报了，继续查为什么心跳丢 |

### 注入验证看计数，不看工具回显

**看注入前后 `number` 是否变化**，不要看工具回显或 `Times` 字段。回显成功不代表真的注入了。

### `cycle_enable` 为 0 = 周期自检没开

客户抱怨「注入了没上报」时，这是高频原因。

**以实际节点为准**：Linux 要同时检查 domain 和 module；当前 QNX SDK 的 BSP domain0 也有 domain + module 两级开关，其他 domain 按实际注册节点检查。

### CPU 负载是大量结论的前提

心跳超时、周期自检超时、FCU handler timeout 这类现象，在 CPU 持续高负载下基本可归因到负载。所以负载查询是必做项。

## 回填后怎么用

逐条对照预期，**明确写出「符合预期 → 排除什么」**。例如：

> - `domain0/cycle_enable` = 1 ✓ 符合预期 → 排除「周期自检未开」
> - `error17/number` = 0，但日志有 12 条 `heartbeat time:` → **命中 FAQ 心跳条目**：去抖过程日志，未真正上报故障
> - `inject_enable` = 1 ✓ → 排除注入总开关

排除项要写依据。这部分直接进交接文档的「已排除」章节，是**最省原厂时间**的内容。

拿到回填后：能定性就出结论；仍不能定性则进 S5 代码反查。

## 找时间线上最早的异常

<EXTREMELY-IMPORTANT>
**抓日志用 `head` 而不是 `tail`**（在已经拿到完整日志的前提下筛选时）。

要找的是时间线上**最早**的异常，不是最后一条。心跳超时、周期自检 overdue、FCU handler timeout 大多是**首个原始故障的下游症状**。按最后一条日志归因几乎必错。

这条两平台都适用，Linux 侧尤其重要（Call trace / RCU stall 场景）。
</EXTREMELY-IMPORTANT>

## 平台特有的强制要求

<EXTREMELY-IMPORTANT>
**Linux**：FCU 同步读取经 RPMsg 转发并不可中断等待，`timeout` 不能保证解除 D 状态。已有读取卡住或通信状态不明时，先取现有任务栈、RPMsg/握手日志及节点信息，停止新增同步读取；通信恢复确认后再串行访问。无响应不等于已证明未建链。

**QNX**：进程存活检查是首要项——四个独立进程（`diag_core_drv`/`diag_extend`/`m57_ecm_drv`/`fcu_drv`）任一挂掉都会导致诊断静默失效。卡死类问题看 `pidin` 的线程阻塞态（REPLY-blocked / RECEIVE-blocked）。
</EXTREMELY-IMPORTANT>
