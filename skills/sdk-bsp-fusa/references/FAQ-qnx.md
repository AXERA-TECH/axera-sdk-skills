## 第一类 · 心跳与「heartbeat」相关

### FAQ-01：串口一直打印 `heartbeat time:N`，是芯片故障吗？

**其他问法**：`heartbeat time` 是什么意思？｜心跳计数一直涨正常吗？｜heartbeat 日志和 heartbeat 超时有什么区别？

**一句话结论**：`heartbeat time:N` 是**连续等待心跳应答超时的计数**，不是收到心跳的次数；故障注入也可触发该分支。等待成功后计数清零，连续计数 `> 5` 才打印 `heartbeat timeout.` 并提交故障事件。仅有 INFO 行不能认定已上报故障，也不能把持续增长一概当作正常保活。

**怎么判断**：

- 结合连续日志判断：`heartbeat time:1～3` 后应答恢复且没有正式超时，可按去抖过程处理；连续增长到 6 或出现 `heartbeat timeout.` / `HeartBeat error` 时，应继续查服务、通信、调度和注入状态。
- M57 FuSa 是**三级心跳链**：Safety Island R 核 ↔ 用户态 diag server ↔ BSP diag_core 驱动，互发心跳，`0xdeadbeef` 是握手/心跳标记。三级各自计数、各自打印，属正常。

**怎么处理**：先区分过程计数与正式超时。未达故障条件且应答恢复时，无需因 INFO 日志单独升级；持续增长或已正式报错时保留上下文继续排查，不直接忽略。嫌 INFO 刷屏可调日志级别（见 FAQ-07）。源码依据：`kernel/osdrv/private_drv/diag_core/driver/diag_stl.c:164-180`，引用时核对当前版本。

**要不要升级**：仅凭过程计数不能决定升级；若已正式超时，再结合版本与现场证据判断。

### FAQ-02：高负载/压测时报心跳超时，是不是 bug？

**其他问法**：CPU 跑满时心跳断了｜压测一会儿就 heartbeat timeout｜心跳线程被饿死｜握手后要等好几秒才有心跳

**一句话结论**：**【已修故障】**老版本确有几个**高负载下心跳超时**的缺陷（线程饿死/线程风暴、ACK 队头阻塞、握手后不立即回心跳干等约 5 秒），**均已修复**；升级到含修复的版本即可。

**怎么判断 / 涉及的已知问题**：

- **心跳线程被饿死 / 线程风暴**：高负载抢不到 CPU → 心跳线程发不出。
- **ACK 队头阻塞**：ACK 处理排在业务后面，堵住心跳回复。
- **握手时序**：握手成功后不立即回第一个心跳，白等约 5 秒。

**怎么处理**：

1. 确认客户版本，落在下表修复版本之前 → 建议升级。
2. 升级后仍报，多半是 CPU 真被打满（见 FAQ-12），保证 **CPU 占用 < 80%**。

**要不要升级**：【已修故障】升级到以下版本即解决：

| 现象 | 修复版本 |
|---|---|
| 线程饿死/风暴（心跳线程提优先级+单并发） | V0.11.0 起 |
| ACK 队头阻塞（移到接收线程处理） | V0.11.0 |
| 握手后不立即回心跳干等 ~5s | V0.16.0 起 |

### FAQ-03：心跳超时的同时刷 `Failed to allocate error node memory`，什么原因？

**其他问法**：报错节点内存分配失败｜r_core_log 太大导致心跳超时｜日志文件撑爆内存

**一句话结论**：**【配置·使用·方法】**多半是 **r_core_log 日志过大**吃光内存，导致上报节点 `malloc` 失败并连带心跳超时。把 r_core_log 限制在 **≤ 1M** 即可规避。

**怎么处理**：

- 检查客户是否把 R 核日志/调试日志开得过大或写到内存文件系统（/tmp）。
- 限制单个日志 ≤ 1M；清理 /tmp。

**要不要升级**： 配置/使用问题，长期有效，控制日志大小即可。

### FAQ-04：QNX 上心跳周期比预期长（约 90ms）、偶发 R 核心跳超时，要优化吗？

**其他问法**：R 核 80ms 超时但实测周期 90ms｜QNX 调度导致心跳偏慢｜周期抖动算不算 bug

**一句话结论**：**【设计预期】**QNX 定时周期实测约 **90–92ms**（略大于 80ms 阈值）属操作系统调度差异，**不是缺陷**；偶发的超时告警是调度抖动，不影响安全功能。

**怎么处理**：向客户解释是 QNX 调度特性；如需更严阈值再评估调度优先级配置。

**要不要升级**：**【设计预期】**设计/调度范畴，非 bug。

## 第二类 · error_mask 错误码怎么读

### FAQ-05：`error_mask` 怎么解码？比如 `0x08000005` 是什么意思？

**其他问法**：诊断错误码怎么拆？｜domain/module/event 怎么算？｜DIAGCORE_ERROR_1~6 分别代表什么？

**一句话结论**：**【设计预期】**`error_mask`（AX_U32）按**三段位域**解码，规则**全版本不变**：

```
域 Domain  = mask >> 27
模块 Module = (mask & 0x7FFFFFF) >> 16
事件 Event  = mask & 0xFFFF
```

**验证样例**：`0x08000005`

- Domain = `0x08000005 >> 27` = **1** → MAIN_SYSTEM
- Module = `(0x08000005 & 0x7FFFFFF) >> 16` = **0** → diag_server
- Event  = `0x08000005 & 0xFFFF` = **5**
- 即：主域系统 / diag_server / 事件 5。

**Domain 枚举对照**：0=MAIN_BSP，1=MAIN_SYSTEM，2=MAIN_PLATFORM，3=MAIN_ADAS，4=SAFETY_BSP，16=MCAL_CDD。

**怎么处理**：拿到 mask 先解出三段，再对照模块/事件语义定位是哪个子系统报的；然后判断是「注入的」「误报的」还是「真故障」。

**要不要升级**：设计预期解码规则是协议约定，全版本通用。

---------



### FAQ-06：这些具体错误码是不是真故障？（误报码速查）

**其他问法**：`0x80000011` / `0x00000012` 是什么？｜周期自检误报｜某个 mask 反复出现是不是 bug

**一句话结论**：下表几个高频 mask 多为**特定场景下的误报**，对号入座即可：

| error_mask | 场景 | 结论 | 性质 | 修复版本/归属 |
|---|---|---|---|---|
| `0x80000011` `0x80000014` `0x00000012` `0x00000013` | 高 CPU 下周期自检**误报** | CPU 打满导致假报，保证 CPU<80% | 已修故障 | V0.16.0 |
| `0x00170000` | ECM_NPU reset 冲突 | NPU 域复位冲突 | 已修故障 | V1.8.0（npu_neutron） |

**怎么处理**：先按 FAQ-05 解码确认三段语义 → 若命中上表，按「修复版本」判断客户版本是否已含修复；周期自检类误报重点确认压测时 **CPU < 80%**。

**要不要升级**：【已修故障】 老版本升级到对应修复版本即解决。

## 第三类 · diag-netlink 刷屏怎么定位

### FAQ-07：串口一直刷 `diag-netlink ... err N module M domain D`，怎么定位？

**其他问法**：diag 日志刷屏怎么关？｜每条 error 打一行正常吗？｜怎么按 module/domain 找来源

**一句话结论**：**【设计预期】**diag_core 对**每条上报的 error 打印一行 INFO**（日志级别默认 7 = info），刷屏本身正常；按行里的 `err/module/domain` 三字段就能定位来源。

**怎么判断**：

- `domain 0`（DFC）+ `err 16/17/18/19` 是最常见的几类：
  - **err 16**：模块注销后漏关中断（见 FAQ-10）
  - **err 17**：server 心跳超时（见 FAQ-09）
  - **err 18**：进程退出/崩溃（见 FAQ-08）
  - **err 19**：error_timeout
- 想少刷屏：调低 diag 日志级别（`DIAG_LOG_LEVEL_VALUE`）。

**怎么处理**：先看 `err` 号归到 FAQ-08~11 对应条目；确认是「注入触发」「退出触发」还是「真故障」。

**要不要升级**：**【设计预期】**打印机制本身是设计；具体 err 号是否 bug 见下面各条。

---------



### FAQ-08：退出 demo / 进程崩溃后刷屏 `err 18 module 0`，正常吗？

**其他问法**：kill 进程后一直报 err18｜demo 退出触发诊断上报｜进程崩溃诊断码

**一句话结论**：**【设计预期】/【已修故障】 混合。**进程异常退出/崩溃会触发 err 18 上报，这是**监控生效的表现**；老版本有过重复上报/误报，已在 **V0.12.0** 收敛。

**怎么处理**：

- 正常退出场景解释为「进程退出被安全监控感知并上报」。
- 若版本较老且重复刷 → 升级到 V0.12.0 起。

**要不要升级**：**【已修故障】**V0.12.0。

---------



### FAQ-09：高负载时刷屏 `err 17 module 0 domain 16`，是 bug 吗？

**其他问法**：CPU 满载报 err17｜server 心跳超时刷屏

**一句话结论**：**【设计预期】**err 17 是 **server 心跳超时**上报；在 CPU 满载时出现是**预期**（超时监控生效），不是缺陷。

**怎么处理**：保证 CPU < 80%（见 FAQ-12）；解释为负载过高触发心跳超时监控。

**要不要升级**：**【设计预期】**（V0.14.0）。

---------



### FAQ-10：ISP/sample_vin 退出约 10 秒后刷屏 `err 16 module 10 domain 16`？

**其他问法**：退出取流后报 err16｜FCU 注销没关中断｜模块卸载后漏报中断

**一句话结论**：**【已修故障】**老版本 FCU 注销时**没关中断**，导致残留中断持续触发 err 16；已补 `fcu_irq_mask`，**V0.15.0** 修复。

**怎么处理**：确认版本 → 老于 V0.15.0 建议升级。

**要不要升级**：**【已修故障】**V0.15.0。

---------



### FAQ-11：reboot / ECM 注入后刷屏 `err 3 module 26`，写入值和回读值明明一样却报 readback error？

**其他问法**：ECM readback odds｜写回校验偶发失败｜寄存器读写竞态

**一句话结论**：**【已修故障】**老版本 ECM 寄存器读写未加锁，并发下回读校验偶发失败（readback odds）；加自旋锁串行化后修复。

**怎么处理**：确认版本 → 命中则升级。

**要不要升级**：**【已修故障】**V0.8.0 / V0.9.0。

## 第四类 · 加压 / 压测稳定性

### FAQ-12：压测（CPU/NPU 加压）后刷屏 `BSP HeartBeat error !!!`，是芯片故障吗？

**其他问法**：跑满负载就报 BSP 心跳错误｜maxpwr 压测报心跳｜heartbeat error 和 CPU 占用有关吗

**一句话结论**：**【已修故障】→【设计预期】 +【使用方法问题】** 早期是心跳窗口设计问题（已在 **V0.16.0** 优化），但根因常是 **CPU 被打满**导致心跳线程发不出。**压测请保证 CPU 占用 < 80%**；心跳窗口 = 20ms × flowTimerLen（默认 4 = 80ms），`flowTimerLen` 可调。

**怎么判断 / 处理**：

1. 先看压测时 CPU 占用，**> 80% 几乎必报**，这是负载问题。
2. 降负载到 CPU < 80% 后仍频繁报 → 确认版本是否 ≥ V0.16.0。

**要不要升级**：**【已修故障】**V0.16.0（相关见 V0.11.0）。

---------



### FAQ-13：压测久了 `malloc` 失败 / core dump 且 core 文件为 0；或压测串口一直刷调试打印？

**其他问法**：长时间压测内存分配失败｜core 文件是空的｜压测刷大量 debug log

**一句话结论**：**【已修故障】** ① r_core_log 撑爆 /tmp 导致 `malloc` 失败（限 ≤ 1M，V0.12.1 修）；② 早期**调试打印刷屏**（V0.8.0 相关）。均已处理。

**怎么处理**：

- malloc 失败：清 /tmp、限制 r_core_log ≤ 1M。
- 刷调试打印：确认版本，老版本升级。

**要不要升级**：**【已修故障】** r_core_log：V0.12.1；调试刷屏：V0.8.0。

---------



### FAQ-14：长稳压测（反复启停 / 跑 20 小时）后不出帧 / 卡死，内存越用越少？

**其他问法**：长时间跑内存泄漏｜/dev/mem 映射泄漏｜CMM pool 被误释放｜跑一夜就卡死

**一句话结论**：**【已修故障】**老版本存在**资源泄漏**——`/dev/mem` 映射累积到十几万个、CMM pool 被误释放，长跑后耗尽资源卡死；已修。

**怎么处理**：确认版本；命中则升级。观察 `/dev/mem` 映射数是否持续增长可辅助定位。

**要不要升级**：**【已修故障】** V1.0.0（相关见 V0.10.0）。

---------



### FAQ-15：高低温箱怎么给 CPU 加压？压测「卡死 / 退不出」怎么判断是不是真故障？

**其他问法**：温循压测方法｜怎么软件加压｜12 秒退出算异常吗｜复现不了怎么办

**一句话结论**：**【配置·使用·方法】** 用**软件加压工具（maxpwr）**给 CPU 加负载，别用温箱过热去逼硬件（过热损了硬件容易误当软件 bug）。压测「退出/卡死」先判断是不是**正常退出被误判**，并**保全现场**再下结论。

**怎么处理**：

- 加压：用 maxpwr 等软件手段，控制在器件规格内。
- 判定：如「12 秒后正常退出」被当异常，先确认退出是否符合用例预期；复现不了/取证不足的单，优先保留日志、core、现场，别急着定芯片。

**要不要升级**：**【配置·使用·方法】** 测试方法/取证问题，长期有效。

## 第五类 · 配置与编译使能

### FAQ-16：FuSa 诊断是怎么编译进来的？改了 Excel 配置为什么不生效？

**其他问法**：怎么打开 FuSa 编译｜fusa_config 是干嘛的｜改了诊断配置表没变化｜generated_diag_config

**一句话结论**：**【配置·使用·方法】**FuSa 由宏 `SUPPORT_AX_DIAG` 使能，配置由 **`make PLAT=xxx fusa_config`** 解析 Excel 生成（`generated_diag_config.py`）。**改完 Excel 必须重跑 `fusa_config` 重新生成**，否则不生效。

**怎么处理**：

1. 确认 `SUPPORT_AX_DIAG` 已打开。
2. 改 Excel 后执行 `make PLAT=<平台> fusa_config` 重新生成配置，再编译。
3. 首次平台适配见 V0.16.0。

**要不要升级**：**【配置·使用·方法】**使用流程；首次适配相关修改在 V0.16.0。

---------



### FAQ-17：Excel 里把某模块（如 mm_cdma）关了，重编后还在 / 开关不独立？

**其他问法**：mm_cdma 关不掉｜两个功能共用一个宏｜假开关

**一句话结论**：**【已修故障】**老版本 **MM_CDMA 与 FBCDC 共用同一个宏**，是「假开关」关不干净；已解耦，**V1.10.0** 修复。

**怎么处理**：确认版本；命中则升级到 V1.10.0 起。

**要不要升级**：**【已修故障】**V1.10.0。

---------



### FAQ-18：编译时关了开关，但 diag_tools 还显示节点 / 功能还在，怎么回事？

**其他问法**：关了诊断还在上报｜编译开关和运行时不是一回事吗｜怎么真正关闭上报

**一句话结论**：**【设计预期】**要区分**编译期开关**和**运行时上报**两层。诊断上报要真正生效/关闭，需要 **diag service 启动**；编译期关某功能，不等于运行时节点全消失。这是分层设计，不是 bug。

Safety 域的故障诊断模块是静态注册的，如果关闭了使能，上报通路是断开的，符合设计预期。

**怎么处理**：

- 想彻底停上报：确认运行时 diag service 状态，而不只是看编译宏。
- 编译期开关控制的是「是否编进」，运行时控制的是「是否上报」。

**要不要升级**：**【设计预期】**。

### FAQ-19：同样配置在不同板子行为不一样？NAND 板 MMC_STL 关不掉 / 开不了？

**其他问法**：NAND 板没有 eMMC 自检｜MMC_STL 被强制关｜换板子配置不一致

**怎么处理**：向客户说明按板型差异化配置；NAND 板无 eMMC 自检属正常。

## 第六类 · 故障注入怎么做

### FAQ-22：M57 QNX FuSa 有几种故障注入方式？分别怎么用？

**其他问法**：怎么注入故障验证诊断｜fault injection 方法｜diag_tools 注入命令

**一句话结论**：**【设计预期】**三条注入通路，按目标层次选：

| 通路 | 面向 | 用法要点 |
|---|---|---|
| ① **BSP diag_core** | 内核/驱动层诊断 | `diag_tools -m <module> -f <event> -i` 写 `/proc/ax_diag`，注入次数可消耗 |
| ② **用户态 STL** | MSP 用户态自检（如 IVE） | `DIAG_TRIG_EVENT` + `AX_DIAG_IsInjection`（见 FAQ-25） |
| ③ **CPU RAS** | CPU 硬件 RAS | `cpu_ras_inject`，经 SMC/ATF（见 FAQ-24） |

**怎么处理**：先明确要验证哪一层的诊断，再选对应通路；注入后按 error_mask 解码（FAQ-05）确认上报正确。

**要不要升级**：**【设计预期】**注入能力是框架特性，全版本可用。

---------



### FAQ-23：注入后 `Times:1` 一直不变、也没有 call-trace，是不是没注入成功？

**其他问法**：Times 不涨正常吗｜注入没打印调用栈｜怎么确认注入生效

**一句话结论**：**【设计预期】** **正常**。`Times:1` 表示「本次注入次数」，不是累计计数，所以不变；注入路径**不产生 call-trace** 也是预期。想确认是否生效，看 **`-s` 输出里的 number 计数**。

**怎么处理**：用 `diag_tools -s` 查看对应事件的 number 是否变化来确认，而不是盯 `Times` 或找 call-trace。

**要不要升级**：**【设计预期】**。

### FAQ-24：CPU RAS 怎么注入？为什么单独注一个 CE 会整机重启 / 连带报 `0x001F0010`？

**其他问法**：cpu_ras_inject 用法｜注入 CE 却复位主域｜CE 注入期间 FAULTIRQ 被屏蔽

**一句话结论**：**【已修故障】** CPU RAS 用 `cpu_ras_inject` 注入。老版本存在 **CE 注入连带触发 UE、复位主域**、以及 **CE 期间 GIC 屏蔽 FAULTIRQ** 的问题；已在 ATF 侧修复，**V0.17.0**。

**怎么处理**：确认版本；命中则升级到 V0.17.0 起再验证 CPU RAS 注入行为。

**要不要升级**：**【已修故障】** V0.17.0。

---------



### FAQ-25：用户态 STL（如 IVE）怎么注入？改了 golden_data 却没有故障码？

**其他问法**：IVE 注入没上报｜周期自检默认没开｜cycle_enable 怎么开｜QNX usleep 太短没用

**一句话结论**：**【设计预期 / 配置·使用·方法】**用户态自检**周期检查默认关闭**，注入前要先开：

```
echo 1 > /proc/ax_diag/domain0/cycle_enable
```
不开周期自检，改了 golden_data 也不会触发上报。另外 QNX 上 `usleep` 最短约 1.5ms，做精细延时要用 `nanospin_ns`。

**怎么处理**：

1. 先 `echo 1 > /proc/ax_diag/domain0/cycle_enable` 开周期自检。
2. 再按用户态注入流程触发，观察上报。

**要不要升级**：**【设计预期】**使用方法。

## 第八类 · FCU 故障汇聚

### FAQ-30：子系统故障是怎么送到 FCU、再通知到用户态的？`/dev/fcu` 接口是什么？

**其他问法**：FCU 上报链路｜/dev/fcu 怎么用｜FCU 怎么跨域汇聚故障

**一句话结论**：**【设计预期】**FCU（Fault Collection Unit）是**故障汇聚单元**，设备节点 `/dev/fcu`；各硬件中断（hwirq）按客户端列表分发，跨域故障通过 rpmsg 汇聚。用户态通过 devctl（如 `DCMD_FCU_REGISTER_CALLBACK`）注册回调接收故障。

**怎么处理**：向客户说明这是统一故障汇聚通道；注册/查询走 `/dev/fcu` 的 devctl 命令族。

**要不要升级**：**【设计预期】**机制说明，全版本有效。

### FAQ-32：`fcu handler timeout` / `0x800A0010` 是 bug 吗？

**其他问法**：FCU handler 超时｜0x800A0010 什么意思｜50ms 超时上报

**一句话结论**：**【设计预期】** **不是 bug**。这是 FCU 的**超时上报设计**：handler 处理超过阈值（默认 **50ms**，HAPS 环境 100ms）就上报 `0x800A0010`。属预期保护机制。

**怎么判断**：

- 解码 `0x800A0010` → 归 FCU（DIAG_MID_FCU_SAFETY），事件为 handler timeout。
- 偶发一次多为处理耗时抖动；持续大量出现才需查处理链路为何变慢。

**怎么处理**：向客户解释是超时保护；若频繁触发，排查对应 handler 为何处理超 50ms（负载、阻塞等）。

**要不要升级**：**【设计预期】**。

---------



### FAQ-33：看似 FCU 超时，其实是 bus_fab 自检卡死，怎么区分？

**其他问法**：bus_fab 自检永久阻塞｜MsgReceivePulse 没超时｜卡在总线自检

**一句话结论**：**【已修故障】**老版本 **bus_fab 自检 `MsgReceivePulse` 没设超时**，收不到脉冲就永久阻塞，表现像「FCU 超时/卡死」；加 `_NTO_TIMEOUT_RECEIVE` 超时后修复，**V0.11.0**。

**怎么处理**：确认版本；命中则升级到 V0.11.0 起。区分点：真 FCU handler timeout 会上报 `0x800A0010`（FAQ-32），而 bus_fab 卡死是**整体阻塞无上报**。

**要不要升级**：**【已修故障】**V0.11.0。
