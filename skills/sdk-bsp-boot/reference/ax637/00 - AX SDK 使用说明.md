### 1.1 编译工具链

由于本SDK支持arm64架构，使用支持arm64架构的gcc version 9.2.1 20191025 (GNU Toolchain for the A-profile Architecture 9.2-2019.12 (arm-9.10))，请您自行至ARM官方网站下载并安装该版本工具链。

官方网站的地址：

https://developer.arm.com/-/media/files/downloads/gnu-a/9.2-2019.12/binrel/gcc-arm-9.2-2019.12-x86_64-aarch64-none-linux-gnu.tar.xz

由于SDK里面包含MCU Boot的代码，因此也需要部署MCU Boot用的交叉编译工具链，使用支持ARM32架构的gcc-linaro-7.5.0-2019.12，请您自行至如下网址下载。

官方网站的地址：

[http://releases.linaro.org/components/toolchain/binaries/7.5-2019.12/arm-linux-gnueabi/gcc-linaro-7.5.0-2019.12-x86_64_arm-linux-gnueabi.tar.xz](http://releases.linaro.org/components/toolchain/binaries/7.5-2019.12/arm-linux-gnueabi/gcc-linaro-7.5.0-2019.12-x86_64_arm-linux-gnueabi.tar.xz)

由于SDK里面包含MCU RT-Thread的代码，因此也需要部署MCU RT-Thread 官方用的交叉编译工具链，使用支持ARM32架构的gcc-arm-none-eabi，请您自行至如下网址下载。

官方网站的地址：

[https://developer.arm.com/-/media/Files/downloads/gnu-rm/5_4-2016q3/gcc-arm-none-eabi-5_4-2016q3-20160926-linux.tar.bz2](https://developer.arm.com/-/media/Files/downloads/gnu-rm/5_4-2016q3/gcc-arm-none-eabi-5_4-2016q3-20160926-linux.tar.bz2)

## 分区大小调整约束：

1. 对于nand场景，由于nand颗粒本身坏块特性（出厂坏块或使用坏块），SDK展示的分区配置文件默认已为各分区预留足够block用作跳坏块(满足生命周期内10ppm不良率要求)，若客户为了极致裁剪分区大小不在乎使用坏块，那么也必须预留block（因为还要考虑出厂坏块的颗粒特性）。

2. 对于nand场景，不像emmc场景 hsm是没有专门的分区的，hsm镜像是附在sbl镜像后面作为256K sbl镜像输出的(前128K是sbl后128K是hsm)，这是受限于Romcode对sbl及hsm的引导导致，因此对于sbl分区中实际sbl镜像占的大小要用256K进行考虑。

3. 对于AB场景下，SBL分区大小无论emmc情况还是nand情况必须用SDK默认展示的（nand 768k, emmc 128K），原因是RomCode找B分区的偏移就是按这个大小来的。

## Nand场景下若客户实在不考虑使用坏块，对于前面几个关键启动分区，可考虑的大小优化：

1. sbl分区大小优化（如前说明 只支持非AB下）

## 若block128：分区可都改128K

## 5. 根文件系统

### 5.1 根文件系统简介

根文件系统（root Filesystem）是内核启动时挂载（mount）的第一个文件系统，如果系统不能从指定设备上挂载根文件系统，会导致系统启动出错。系统启动成功之后可以自动或手动挂载其他文件系统。很明显，一个系统中是可以同时存在不同的文件系统的。

根文件系统的“根”说明该文件系统是加载其他文件系统的“根”，否则其他的文件系统无法进行挂载。根文件系统被挂载在根目录“/”之下，在根目录下就存在该文件系统的各个目录和文件，比如/bin、/sbin、/mnt等，然后可以将其他文件系统挂载在/mnt目录下。

根文件系统包含系统启动时所必须的目录和关键性文件，以及挂载其他文件系统所必须的文件。如下图所示：

![fig 5 1](ax_sdk_usage_00_assets/fig_5_1.png)

因此，内核必须要和根文件系统相互配合才能工作，只有内核本身是无法工作的。

### 5.2 利用Buildroot制作根文件系统

Buildroot 是一个强大且灵活的自动化构建工具，专门用于创建定制的嵌入式 Linux 系统。它通过一个基于 Kconfig（类似 Linux 内核的配置系统）的 `make menuconfig` 界面，允许开发者精确选择目标硬件架构（如 ARM、ARM64、x86）、交叉编译工具链（可由 Buildroot 构建或使用外部预编译版本）、C库（如 glibc, uClibc-ng, musl）、Linux内核版本及配置、引导加载程序（如 U-Boot）以及根文件系统中所需的各种用户空间软件包和库（从基础的BusyBox工具集到复杂的应用程序如GStreamer或Python）。

配置完成后，执行 `make` 命令，Buildroot 会自动下载所有选定组件的源代码，编译交叉工具链，然后用此工具链编译内核、引导加载程序和所有用户软件包，最后将它们组装成一个完整的根文件系统镜像。支持多种镜像格式，如 `tar` 包、`ext2/3/4` 分区镜像、`cpio` (常用于 initramfs)、`squashfs` 等。Buildroot 还提供了如文件系统覆盖 (overlay) 和构建后脚本等机制，方便开发者进行深度定制，例如添加自定义文件、修改配置或执行特定设置。最终，Buildroot提供了一个可复现的、高效的、高度可定制的方法来为嵌入式设备生成完整的、可启动的Linux系统。

### 5.3 文件系统简介

#### 5.3.1 SquashFS

SquashFS是专门为一般的只读文件系统的使用而设计，它可应用于数据备份，或是系统资源紧张的电脑上使用。最初版本的SquashFS采用gzip的数据压缩。版本2.6.34之后的Linux内核增加了对LZMA和LZO压缩算法的支持，版本2.6.38的内核增加了对LZMA2的支持，该算法同时也是xz使用的压缩算法。

版本2.6.35之后的内核包含的SquashFS增加了扩展文件属性支持。

#### 5.3.2 EXT4

EXT4的全称是Fourth extended filesystem，是Linux系统下的日志文件系统，是EXT3文件系统的后继版本。

#### 5.3.3 UBIFS

无序区块映像文件系统（Unsorted Block Image File System，UBIFS）是一种用于固态硬盘存储设备的文件系统，UBIFS最早在2006年由IBM与Nokia的工程师Thomas Gleixner，Artem Bityutskiy所设计，专门为了解决MTD（Memory Technology Device）设备所遇到的瓶颈。由于Nand闪存容量的暴涨，YAFFS等皆无法再去控制Nand闪存的空间。UBIFS透过子系统UBI处理与MTD设备之间的动作。与JFFS2一样，UBIFS建构于MTD设备之上，因而与一般的块设备不兼容。

UBIFS在设计与性能上均较YAFFS2、JFFS2更适合大容量的NAND FLASH。例如，UBIFS支持write-back，其写入的资料会被缓存，直到有必要写入时才写到闪存，大大地降低分散小区块数量并提高I/O效率。UBIFS文件系统目录存储在闪存上，UBIFS挂载时不需要扫描整个闪存的资料来重新创建文件目录。

## 6. 日志系统

### 6.1 日志系统简介

日志系统是记录操作系统、驱动、应用所产生的Log的一套服务程序。这套服务程序主要由syslogd、klogd、axsyslogd以及axklogd组成。klogd记录Linux内核原生的内核Log，syslogd根据/etc/syslog.conf的配置来记录系统Log，syslogd和klogd是busybox自带的一组log服务程序，通过/etc/init.d/S01syslogd和/etc/init.d/S02klogd服务来启动，自动保存log。而axsyslogd和axklogd是本SDK开发的一组记录SDK自研实现的非开源驱动log和 应用程序log的服务程序，应用程序log直接由axsyslogd记录，而axklogd记录驱动的log并转发给axsyslogd，所有log最终由axsyslogd统一写入到同一个log文件中。

！注意：

SDK中的日志总体包含两个部分：

- Linux系统原生日志，包含Linux内核原生日志及基础应用程序日志；

- SDK自研驱动日志及SDK自研应用、动态库、静态库产生的日志。

本章着重介绍SDK自研驱动日志及SDK应用、动态库、静态库产生的日志的控制、抓取以及查看等。

- 本章中提到的user log，如未特别表明，均指SDK自研应用、动态库、静态库等用户态程序所产生的日志。

- 本章中提到的kernel log，如未特别表明，均指SDK自研驱动程序所产生的日志。

其中，config配置的是ax_syslog.conf配置文件路径，您可以修改为您需要的路径，比如：/etc/init.d/my_syslog.conf，这样axsyslogd会自动去读取/etc/init.d/my_syslog.conf文件的配置信息<span style="color:#000000">。</span>

该文件配置包含两部分功能：

###### log存储配置

log存储配置，说明如下：

1. `AX_SYSLOG_enable`  1：保存log，0：不保存log（log仍然可能在输出，只是未存储）。

2. `AX_SYSLOG_path`    log存储路径，不支持ramfs分区。例如，通过mount -t ramfs /dev/xxx /log/dir得到的/log/dir无法将Log保存下来，原因是这种方式得到的分区无法获取分区大小，请避免使用该方式得到的分区，如果需要使用ram分区来保存Log，推荐使用tmpfs分区。

3. `AX_SYSLOG_percent`为避免磁盘被写log写满，通过该配置值，控制Log的输出量，当磁盘占用空间超过该值时，log系统会进行循环覆盖或停止保存log（由`AX_SYSLOG_strategy`决定）。

4. `AX_SYSLOG_strategy`  log存储策略，磁盘空间受限后，新log是覆盖旧log，还是丢弃。0:覆盖, 1:丢弃。

5. `AX_SYSLOG_filesizemax` 单个log文件的大小，请务必保证至少可以保存两个log文件，即`AX_SYSLOG_filesizemax`*2 <= `AX_SYSLOG_volume`。

6. `AX_SYSLOG_volume` 存储log的总大小，当存储的log文件大小超过该值时，开始循环覆盖或者丢弃log（由`AX_SYSLOG_strategy`决定）。

7. `AX_SYSLOG_minimalspace` log系统会尽可能多的保存Log，以2GB的总空间为例，`AX_SYSLOG_percent` = 80，`AX_SYSLOG_minimalspace` = 256的配置，当磁盘写到1638.4MB时，剩余的可用空间为409.6MB，这个值大于`AX_SYSLOG_minimalspace`，所以Log会继续保存，直到可以空间小于256MB，Log开始循环覆盖。相反，如果总空间为1GB，`AX_SYSLOG_percent` = 80，`AX_SYSLOG_minimalspace` = 256的配置，那么当可用空间小于`AX_SYSLOG_minimalspace`时，Log仍然会保存到磁盘的80%，然后开始循环覆盖。请根据你的实际磁盘空间来配置这两项值。

<span style="color:#FF6600">系统时间</span> kernel: [内核时间] <span style="color:#008000">[CPU]</span><span style="color:#FFCC00">[模块名]</span><span style="color:#FF00FF">[log类型]</span><span style="color:#0000FF">[线程id]</span> <span style="color:#172B4D">Log内容</span>

其中：

系统时间：log输出时的系统时间

[内核Log时间] 从开机开始计算的内核时间

[CPU] AX637 CPU为2核，取值区间为C0-C1

[log类型]

M: eMergency

A: Alert

C: Critical

E: Error

W: Warning

N: Notic

I: Information

D: Debug

[线程id] 输出Log所属线程ID

[模块名] 输出Log所属模块

### 6.6 动态修改Log等级

#### 6.6.1 动态修改Linux内核原生Log等级

对于Linux原生内核log，即通过printk输出的log，可以通过/proc/sys/`kernel/printk`节点来动态控制输出到串口的linux log等级。默认情况下，Linux原生内核Log的等级配置为4(warning)，这可以通过cat `/proc/sys/``kernel/printk`来查看：

```bash
cat /proc/sys/kernel/printk
```

```text
4       4       1       7
```

如果要修改输出到终端的Log等级，比如修改到等级7，可以通过下面指令来实现：

```bash
echo 7 > /proc/sys/kernel/printk
```

关于printk log等级设置的更多用法，可参考内核文档linux-6.1.83/Documentation/core-api/printk-basics.rst。

#### 6.6.3 动态修改user log等级

我们的log系统支持按模块进行log等级修改，每个模块都有自己对应的ID，比如ISP、VO和NPU他们对应的模块ID分别是１、３、６。确定模块对应的ID值的方式有两种：

      1. 通过cat /etc/ax_syslog.conf文件查看；

      2. 通过cat `/proc/ax_proc/logctl`节点查看。

在ax_syslog.conf配置文件中，我们有一段这样的配置：

#模块Log等级设置

```c
ulog_state  = on
ulog_target = file
klog_state  = on
```

#module id level(user) level(kernel)

ISP     1        4         4

CE      2        4         4

....

以ISP模块为例，其id为1，user log等级为4，这表示ISP模块user log等级为0-4的Log能够被输出，而等级为5-7的Log将被忽略。如果您需要修改模块的默认等级，可以在ax_syslog.conf配置文件修改并保存。

为了方便对user log等级控制，我们提供了根据模块id来控制log等级的指令。指令格式如下：

```bash
echo ulog [id] [level] > /proc/ax_proc/logctl
```

其中ulog表示控制user log等级，id为模块ID，比如ISP的模块ID为1，level为控制log输出的等级，而/proc/ax_proc/logctl为控制log等级的设备节点。为更好地展示如何控制user log的等级，我们举例说明。

示例1：把ISP模块的user log输出等级设置为7，可通过指令：

```bash
echo ulog 1 7 > /proc/ax_proc/logctl
```

来实现，修改后可通过:

```bash
cat /proc/ax_proc/logctl
```

#### 6.6.4 动态修改kernel log等级

kernel log等级的控制与user log等级的控制方式基本一致，只需将命令中的ulog改成klog，最大的差异在于user log能够控制输出到console终端，但kernel log只能输出到日志文件。

以下举例演示如何控制kernel log的输出。

示例1：把ISP模块的log输出等级设置为7，可通过指令：

```bash
echo klog 1 7 > /proc/ax_proc/logctl
```

来实现，修改后可通过:

```bash
cat /proc/ax_proc/logctl
```

![fig 6 7](ax_sdk_usage_00_assets/fig_6_7.png)

示例2：将所有模块的kernel log等级修改为3

```bash
echo klog all 3 > /proc/ax_proc/logctl
```

查看修改结果：

![fig 6 8](ax_sdk_usage_00_assets/fig_6_8.png)

示例3：关闭/打开kernel log输出

```bash
echo klog off > /proc/ax_proc/logctl
```

查看结果

![fig 6 9](ax_sdk_usage_00_assets/fig_6_9.png)

## 8. U-Boot移植应用开发指南

<a id="_概述"></a>

### 8.1 概述

Linux的启动需要有bootloader来引导，AX637系列单板的bootloader可选使用U-Boot，当选用的外围芯片信号与参考设计不同时，需要修改U-Boot的相关配置文件。

#### 8.1.1 AX637启动流程介绍

AX637芯片整体启动流程如下：

![fig 8 1](ax_sdk_usage_00_assets/fig_8_1.png)

如上图，在芯片上电POR（Power On Reset）后，R5F BootROM首先负责完成Safety域基础的初始化，包含不限于power、clock和OCM等硬件的初始化。然后将R5F SBL固件从Nor/Hyper/Nand flash或者eMMC中加载到Safety域的OCM，并解密验签保证SBL镜像的完整性和合法性。最后将R5F CPU的控制权递交给SBL。

R5F SBL开始运行后，首先负责初始化和配置Main域侧的硬件，包含但不限于Power、clock和OCM等硬件的初始化，然后将A55 SPL固件从Nor/Nand/Hyper Flash或者eMMC中加载到Main域OCM上，并验证和校验SPL镜像的合法性和完整性，最后触发A55 CPU开始执行SPL。

SPL开始运行后，首先负责完成DDR的初始化，并配置必要的硬件进入工作状态，包含不限于power、clk、reset和pinctrl等设置。然后将BL31、OP-TEE和U-Boot镜像加载到DDR。最后将A55 CPU控制权交给BL31。

BL31运行后，首先完成EL3 vector table、MMU、PSCI和GIC等初始化，然后初始化SPD的上下文环境，为OP-TEE的运行做准备。最后通过ERET指令跳转到OP-TEE OS。

OP-TEE开始运行，首先完成EL1 secure vector table、UART、MMU、GIC和thread context等初始化。然后执行SMC指令返回到BL31，接着BL31为跳转到BL33做准备。最后BL31执行ERET指令将CPU控制权交给U-Boot。

进入U-Boot运行阶段，首先完成EL2 context、C runtime environment、UART等初始化。然后完成eMMC、Flash等驱动的执行，以及env变量的加载。最后从eMMC/flash里面加载Kernel和dtb等镜像，并验签校验，保证镜像的合法性和完整性，将CPU控制权递交给Kernel。

进入Kernel之后，挂载rootfs，开始完成OS相关的各种初始化和应用程序的启动，超出了本节的范围，不再详细的描述。本节主要介绍在AX637单板上如何移植、烧写U-Boot以及相关debug方法。

### 8.4 uboot引导内核方式说明

#### 8.4.1 SDK默认引导方式

目前uboot引导内核走的是：distro_bootcmd  (引导方式 menuconfig可改)

![uboot sdk plat ax637 demo only nand distro bootc](ax_sdk_usage_00_assets/uboot_sdk_plat_ax637_demo_only_nand_distro_bootc.png)

拿PLAT=ax637_demo_only_nand 举例说明distro_bootcmd流程：

distro_bootcmd –> bootcmd_blk_extlinux -> boot_extlinux -> sysboot mtd 0:9 any 0x10f000000 /extlinux/extlinux.conf -> sysboot

sysboot源码核心实现:

1. 从指定设备分区自动探测文件系统

2. 读取extlinux.conf 配置

3. 按配置文件指定的镜像进行加载：比如加载kernel到 ${kernel_addr_r}，加载设备树到 ${fdt_addr_r}，最后根据加载到内存的镜像格式决定调用哪个引导命令(booti/bootm)

## 相关配置文件内容（extlinux/extlinux.conf）：

## ## extlinux/extlinux.conf

## ##

## default m57_base

## menu title Axera Boot Options

## prompt 0

## timeout 0

## label m57_base

## kernel /Image.axgzip

## fdt /ax637-demo-only-nand.dtb

## 相关环境变量内容：

```c
devnum=0
devtype=mtd
distro_bootpart=9
prefix=/
boot_syslinux_conf=extlinux/extlinux.conf
scriptaddr=0x10f000000
kernel_addr_r=0x110000000
fdt_addr_r=0x118000000
boot_extlinux=sysboot ${devtype} ${devnum}:${distro_bootpart} any ${scriptaddr} ${prefix}${boot_syslinux_conf}
bootcmd_blk_extlinux=   if test -e ${devtype} ${devnum}:${distro_bootpart}       ${prefix}${boot_syslinux_conf}; then     echo Found ${prefix}${boot_syslinux_conf};     run boot_extlinux;     echo BOOT EXTLINUX FAILED;   else     echo Not found ${prefix}${boot_syslinux_conf} on            ${devtype} ${devnum}:${distro_bootpart};     exit -2; fi
bootcmd_dhcpboot= if test -n ${serverip}; then   setenv autoload yes;   setenv bootargs rdinit=/init rw loglevel=10;   dhcp ${kernel_addr_r} ${kernel_name};   dhcp ${fdt_addr_r} ${fdtfile};   dhcp ${ramdisk_addr_r} ${ramdisk_name};   if test $? -ne 0; then     booti ${kernel_addr_r} - ${fdt_addr_r};   else     fdt addr ${fdt_addr_r};     fdt resize;     fdt chosen ${ramdisk_addr_r} ${filesize};     booti ${kernel_addr_r} - ${fdt_addr_r};   fi; else   echo serverip not set; fi
bootcmd_tftp= if test ! -e ${ipaddr}; then   setenv autoload 0;   dhcp;   if test $? -ne 0; then     echo dhcp failed;     exit -2;   fi; fi; if test -n ${serverip}; then   ping ${serverip};   if test $? -ne 0; then     echo ping failed;     exit -2;   fi;   setenv bootargs rdinit=/init rw loglevel=10;   tftpboot ${kernel_addr_r} ${kernel_name};   tftpboot ${fdt_addr_r} ${fdtfile};   tftpboot ${ramdisk_addr_r} ${ramdisk_name};   if test $? -ne 0; then     booti ${kernel_addr_r} - ${fdt_addr_r};   else     fdt addr ${fdt_addr_r};     fdt resize;     fdt chosen ${ramdisk_addr_r} ${filesize};     booti ${kernel_addr_r} - ${fdt_addr_r};   fi; else   echo serverip not set; fi
boot_targets=blk_extlinux tftp dhcpboot
distro_bootcmd=for target in ${boot_targets}; do run bootcmd_${target}; done
bootcmd=run distro_bootcmd
```

##### 基础功能

AX637参考board的U-Boot中支持网络功能，有些U-Boot的场景可以使用网络功能。

举例使用网络给u-boot传输镜像，步骤如下所示：

1. 在本地或者Linux服务器端建立tftp server和DHCP server，具体可参考网上案例（例如tftpd64）。

2. 在u-boot启动过程中按键，进入cmd模式。

3. 输入DHCP分配IP地址。

4. 在板子cmd命令行输入tftpboot 0x40200000 <server-ip>:xxx.bin命令，其中，<server-ip>为服务器端IP地址，请根据具体的Server IP修改。

如上，通过单板连入网络，将server端bin文件传输到开发板内存地址x40200000。

Windows dhcp server软件下载官网：[http://www.dhcpserver.de/cms/](http://www.dhcpserver.de/cms/)

##### 扩展功能——TFTP网络升级

###### 实现原理

1. SDK新增开机tftp_ota启动模式场景，循环处理2、3完成所有升级镜像的写入

2. 通过tftpboot命令将Linux服务器端布置正确的升级镜像文件通过网络传输到板端内存

3. 将内存数据写入镜像文件对应的flash分区(支持的flash有emmc、nand、nor)

###### 使用步骤

### 重要说明

升级过程出现中断的情况：

（1）不支持掉电

如果正好在升级u-boot分区对应的bin文件时未完成掉电，则无法再次启动，必须通过其它方式刷机（如AXDL工具升级）；

如果升级其它文件时掉电升级失败，且客户u-boot方案默认设计没有关闭bootdelay，则还可以继续通过串口进入u-boot console重新配置env进行升级

（2）升级过程中断网

升级过程中断网导致失败，不会影响eMMC数据的写入，如客户u-boot方案默认设计没有关闭bootdelay，则还可以继续通过串口进入u-boot console重新配置env进行升级

- 注意事项：

- 请确保XML文件中的分区信息与uboot代码中的分区信息定义保持一致，否则升级后可能无法启动；

- ota升级设置中若使能了ota_repartition选项，在升级过程中会使用xml中的分区信息进行烧录，建议设置使能；

### 9.3 Acore调频说明

Acore调频链路主要由Kernel初始化、DTS配置、thermal联动以及userspace sample共同完成。

#### 9.3.1 开机默认频率设置

AX637R平台默认将Acore启动到**1.398GHz**。<br>当前默认频率由板级DTS中的CPU PLL初始化参数决定，Linux启动后会将CPU PLL设置到默认频点，并作为cpufreq policy的初始频率。

在ax637r-demo-only-emmc.dts和ax637r-demo-only-nand.dts中，可以看到CPU默认频率相关配置：

## &main_pll_clocks {

## assigned-clocks = <&cpu_pll_1296m>;

## assigned-clock-rates = <1398000000>;

## };

同时CPU节点绑定了OPP表：

## &cpu0 {

```c
clocks = <&cpu_pll_1296m>;
clock-names = "cpu";
operating-points-v2 = <&cpu_opp_table>;
};
```

cpu_opp_table位于板级DTS文件中，用于描述Acore支持的频点集合。当前OPP表中的频点包括：

## 648000000Hz

## 864000000Hz

## 1080000000Hz

## 1296000000Hz

## 1398000000Hz

## 1596000000Hz

修改OPP时，需要同步确认CPU PLL能力、默认启动频点、thermal限频范围以及sample中的限频参数，避免出现频点不匹配或上下限冲突。

Linux启动并完成pll ctrl init后，Acore的默认频率进入1.398GHz，后续再根据governor、thermal策略或userspace控制进行动态调整。

**默认频率修改方法**：

修改Acore默认频率时，需要先确认目标频率是否已经存在于cpu_opp_table中。

1.目标频率已经存在于OPP表

例如，将默认频率修改为1.296GHz。当前OPP表中已经存在：

opp-1296000000 {

	opp-hz = /bits/ 64 <1296000000>;

	clock-latency-ns = <600000>;

};

此时只需要修改assigned-clock-rates：

&main_pll_clocks {

	assigned-clocks = <&cpu_pll_1296m>;

	assigned-clock-rates = <1296000000>;

};

如果需要将默认频率修改为1.596GHz，也可以直接使用已有的OPP频点：

&main_pll_clocks {

	assigned-clocks = <&cpu_pll_1296m>;

	assigned-clock-rates = <1596000000>;

};

当目标频率已经存在于OPP表时，不需要新增OPP节点。

2.目标频率不存在于OPP表

例如，需要将默认频率设置为1.5GHz，而当前OPP表中没有1500000000Hz，此时不能只修改：

assigned-clock-rates = <1500000000>;

需要先在cpu_opp_table中新增对应的OPP节点：

opp-1500000000 {

	opp-hz = /bits/ 64 <1500000000>;

	clock-latency-ns = <600000>;

};

然后再修改默认频率配置：

&main_pll_clocks {

	assigned-clocks = <&cpu_pll_1296m>;

	assigned-clock-rates = <1500000000>;

};

如果新增、删除或调整OPP频点，cooling state与实际频率的对应关系也会发生变化。例如，删除一个OPP频点后，后续cooling state对应的频率可能发生变化，需要重新检查DTS中的cooling-device配置。

以下为performance策略下开启kernel thermal自动降频时使用的DTS配置示例。当前默认采用userspace策略，该配置块通过#if0默认关闭。

当前cpufreq cooling device对应关系如下：

| cooling state | 对应频率 |
| --- | --- |
| 0 | 1596MHz |
| 1 | 1398MHz |
| 2 | 1296MHz |
| 3 | 1080MHz |
| 4 | 864MHz |
| 5 | 648MHz |

当前DTS中的thermal配置如下：

## &cpu_thm {

## cooling-maps {

## /* 80°C: cap at 1080MHz (level 0→3) */

## map0 {

```c
trip = <&threshold>;
```

## cooling-device = <&cpu0 0 3>, <&cpu1 0 3>,

## <&cpu2 0 3>, <&cpu3 0 3>;

## };

## /* 105°C: cap at 864MHz (level 0→4) */

## map1 {

```c
trip = <&target>;
```

## cooling-device = <&cpu0 0 4>, <&cpu1 0 4>,

## <&cpu2 0 4>, <&cpu3 0 4>;

## };

## /* 115°C: cap at the minimum OPP */

## map2 {

```c
trip = <&soc_crit>;
```

## cooling-device = <&cpu0 0 THERMAL_NO_LIMIT>,

## <&cpu1 0 THERMAL_NO_LIMIT>,

## <&cpu2 0 THERMAL_NO_LIMIT>,

## <&cpu3 0 THERMAL_NO_LIMIT>;

## };

## };

## };

其中，map0中的cooling-device = <&cpu0 0 3>表示温度超过threshold后，thermal framework允许CPU从cooling state 0逐步降到cooling state 3，按照当前OPP表，最终频率上限为1080MHz。

例如，删除最高频率1596MHz对应的OPP，OPP表变为：

| cooling state | 对应频率 |
| --- | --- |
| 0 | 1398MHz |
| 1 | 1296MHz |
| 2 | 1080MHz |
| 3 | 864MHz |
| 4 | 648MHz |

此时，原来的map0配置：

cooling-device = <&cpu0 0 3>;

对应的最大降频状态将变为864MHz，而不再是原来预期的1080MHz。如果希望threshold触发后仍然将CPU最高限制到1080MHz，需要同步修改为：

cooling-device = <&cpu0 0 2>,

		 <&cpu1 0 2>,

		 <&cpu2 0 2>,

		 <&cpu3 0 2>;

map1同理需要修改。

map2中的：

cooling-device = <&cpu0 0 THERMAL_NO_LIMIT>;

会根据当前CPU cooling device的最大状态自动生效，通常不需要手动修改。

修改完成后，需要重新编译对应平台的DTB，并在Linux启动后通过以下节点确认频率配置是否生效：

```bash
cat /sys/devices/system/cpu/cpufreq/policy0/scaling_available_frequencies
cat /sys/devices/system/cpu/cpufreq/policy0/scaling_cur_freq
cat /sys/devices/system/cpu/cpufreq/policy0/scaling_max_freq
```

其中，scaling_available_frequencies用于确认OPP频点是否已经加载，scaling_cur_freq用于查看当前Acore频率，scaling_max_freq用于查看当前cpufreq policy允许的最高频率。

### 9.3.2 Acore调频流程

Acore调频流程如下：

1. Kernel初始化阶段

- clk/pll初始化默认将Acore设置到1.398GHz；

- cpufreq创建policy0并绑定OPP表；

- thermal根据DTS注册cpu_thm和相关cooling关系。

2.DTS策略阶段

- DTS定义默认OPP和初始频点；

- userspace策略下关闭cooling-maps，由sample接管；

- performance策略下打开cooling-maps，由kernel thermal自动限频。

3.运行阶段

- userspace下由sample_dfs_thermal读温度、写sysfs调频；

- performance下由thermal framework根据trip点自动降频。

#### 9.3.3 如何查看与手动调频

Linux下可通过sysfs直接查看和修改频率：

查看当前频率：

```bash
cat /sys/devices/system/cpu/cpufreq/policy0/scaling_cur_freq
cat /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
cat /sys/class/thermal/thermal_zone0/temp
```

切换governor：

```bash
echo userspace > /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
echo performance > /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
```

在userspace governor下手动设频：

```bash
echo 1080000 > /sys/devices/system/cpu/cpufreq/policy0/scaling_setspeed
```

限制最大/最小频率：

```bash
echo 1296000 > /sys/devices/system/cpu/cpufreq/policy0/scaling_max_freq
echo 648000 > /sys/devices/system/cpu/cpufreq/policy0/scaling_min_freq
```

### 9.4 DFS调频策略说明

AX637R当前支持两种调频策略：

#### 9.4.1 userspace策略

该策略用于**用户态接管调频**。

特点如下：

- 默认不启用kernel thermal自动调频；

- cpu_thm的cooling-maps默认在DTS中关闭；

- 由sample_dfs_thermal读取thermal zone温度；

- sample根据温度阈值主动写scaling_setspeed；

- 若scaling_setspeed不可写，则退化为写scaling_max_freq。

#### 9.4.2 performance策略

该策略用于**kernel thermal自动调频**。

特点如下：

- 由thermal framework根据温度自动限频；

- 依赖cpu_thm、cooling-maps、#cooling-cells=<2>等DTS配置；

- thermal zone触发trip point后，kernel会通过cpufreq cooling device自动限制CPU频率；

- 不需要userspac esample常驻接管。

#### 9.4.3 如何切换两种策略

两种策略的切换方式有两层：

**1）运行时governor切换**

```bash
echo userspace > /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
echo performance > /sys/devices/system/cpu/cpufreq/policy0/scaling_governor
```

**2）DTS策略切换**

- userspace策略：保持ax637r-demo-only-emmc.dts和ax637r-demo-only-nand.dts中&cpu_thm的cooling-maps注释状态；

- performance策略：打开&cpu_thm下的cooling-maps，并重新编译DTB。

如果启用performance策略，建议同时确认：

```c
CONFIG_CPU_THERMAL=y
CONFIG_CPU_FREQ_THERMAL=y
CONFIG_CPUFREQ_DT=y
CONFIG_THERMAL=y
```

#### 9.4.4 thermal联动方式

AX637R的thermal联动链路为：

thermal sensor -> cpu_thm -> cooling-maps -> cpufreq cooling device -> CPU PLL

具体过程如下：

1.thermal sensor上报温度；

2.cpu_thm根据trip point判断是否需要降频；

3.cooling-maps将trip point绑定到CPU cooling device；

4.thermal framework更新cooling state；

5.cpufreq框架将cooling state映射为频率上限；

6.CPU PLL最终变更到目标频点。

如果使用userspace策略，则thermal framework不自动控制CPU cooling device，而是由sample主动读取温度并写sysfs。

### 9.5 sample使用说明

当前userspace温控sample位于：

`msp/sample/dfs_thermal`

生成的可执行文件为：

sample_dfs_thermal

#### 9.5.1 sample作用

该sample用于在userspace governor下完成温度监控与DFS控制，主要能力包括：

- 读取thermal zone温度；

- 识别cpu_thm；

- 根据温度阈值自动降频/升频；

- 优先写scaling_setspeed；

- 不支持时自动fallback到scaling_max_freq；

- 支持查看当前thermal/cpufreq状态；

- 支持切换governor；

- 支持修改thermal zone mode。

#### 9.5.2 默认调频逻辑

sample默认采用三级温度策略：

- 温度低于一级阈值减去回滞：恢复到最高频；

- 一级阈值到二级阈值之间：限制到一级限频；

- 二级阈值到三级阈值之间：限制到二级限频；

- 高于三级阈值：限制到最低OPP。

默认参数如下：

## 一级阈值：80000m°C

## 二级阈值：105000m°C

## 三级阈值：115000m°C

## 一级限频：1080000kHz

## 二级限频：864000kHz

## 三级限频：最低OPP

## 回滞：2000m°C

### 9.5.3 Sample参数说明

执行sample_dfs_thermal -h可以查看帮助信息，主要参数如下：

## -i <ms>：轮询周期，默认1000ms

-p <dir>：cpufreq policy路径，默认/sys/devices/system/cpu/cpufreq/policy0

-z <dir>：thermal zone路径，默认自动查找cpu_thm

## -w <mc>：一级阈值，默认80000

## -t <mc>：二级阈值，默认105000

## -C <mc>：三级阈值，默认115000

## -c <kHz>：一级限频值，默认1080000

## -m <kHz>：二级限频值，默认864000

-k <kHz>：三级限频值，默认自动取最低OPP

## -y <mc>：温度回滞，默认2000

## -s：查看当前thermal/cpufreq状态

-G <gov>：切换scaling_governor

### 9.5.4 sample启动方式

## 启动监控模式：

## sample_dfs_thermal &

## 查看当前状态：

## sample_dfs_thermal -s

## 切换governor：

## sample_dfs_thermal -G userspace

## sample_dfs_thermal -G performance

## 在userspace下直接设频：

## sample_dfs_thermal -F 1080000

修改thermal zone模式：

## sample_dfs_thermal -Z disabled

## sample_dfs_thermal -Z enabled

在userspace策略下启动sample后，sample会自动将对应thermal zone设为disabled，以避免kernel thermal与userspace同时控制CPU频率。

### 9.5.5 userspace策略下的使用方法

当系统使用userspacegovernor时，建议按以下方式使用sample：

1.切换CPU governor：

## sample_dfs_thermal -G userspace

2.启动sample：

## sample_dfs_thermal &

3.sample会自动：

- 读取cpu_thm温度；

- 判断当前是否超过阈值；

- 写scaling_setspeed或scaling_max_freq；

- 在温度下降后自动恢复频率。

### 9.5.6 sample与thermal的联动关系

在userspace策略下，sample与thermal的关系是：

- thermal zone负责提供温度数据；

- sample负责决策调频动作；

- sample会在接管时将thermal zone暂时设为disabled，避免kernel thermal和userspace同时控制CPU频率；

- sample退出时会恢复thermal zone，并尽量恢复原有频率与限频状态。

因此，userspace策略下的调频不是kernel自动完成，而是**sample主动控制sysfs节点完成**。

## 10. SDK OS Memory统计

### 10.1 概要说明

#### 10.1.1 需求背景

在进行稳定性问题分析时，内存泄漏问题分析比较困难，在发生内存泄漏的时难以确认哪个模块或者哪个进程发生了内存泄漏。如果在内存使用的时候进行统计某个模块分配的系统内存空间大小和次数等，以及内存需求的计算，当出现内存问题的时候就会方便进行优化。

SDK提供了OS Memory的统计功能，可以分模块统计每个模块申请的系统内存大小以及申请内存的次数，简称OS_MEM。

- **注意：**必须使用OS_MEM提供的内存申请API，OS_MEM才会进行统计相关信息。

#### 10.1.2 支持的功能

- 同时支持应用态和内核态的内存统计；

- 能同时统计每个模块对应申请的内存大小和申请次数；

- 针对内核的分配，大小计算支持aligned操作，aligned策略和linux版本保持一致；

- 支持名字为common的ID，方便给osal等一些不属于具体模块的内存申请；

- 支持多种统计策略，在小内存的软件中，只统计申请的次数，不记录每次申请的ID和大小；对于大内存统计更加详细，该开关可以通过/proc节点来配置，默认是小内存，减少统计的内存消耗和时间开销；

- 提供显示某个模块内核态内存的大小和mod_id/sub_id的详细信息。

#### 10.1.3 不支持的功能

- 不支持单个模块内核或者用户态申请的内存大于4GB，但是支持内核态和用户态申请的内存总和大于4GB；

- 不支持没有调用OS_MEM接口的内存统计，例如C++的new/delete、系统的文件cache。

#### 10.1.4 统计策略

policy：引入统计策略是为了os_mem可以应用于不同的场景，目前支持0-2共3个policy；

- 0：OS_MEM分配内存可以支持多进程，统计只能统计多进程的次数，不支持统计多进程申请内存的大小；

- 1：OS_MEM可以统计每个模块分配内存的次数，每个模块每次分配的内存大小。在计算最大分配次数和分配内存大小的时候，只统计当前正在运行的所有进程的历史最大分配次数和分配大小，不包括已经关闭的进程的内存分配；

- 2：OS_MEM可以统计每个模块分配内存的次数，每个模块每次分配的内存大小。在计算最大分配次数和分配内存大小的时候，统计从开机到当前所有进程的最大分配次数和分配大小，包括已经关闭的进程的内存分配；

policy可以通过文件节点来配置，默认使用0 plicy（CPU loading影响最小，内存占用最小），如果要统计详细信息，可以在所有模块的ko load之前通过echo 节点进行配置；

方法如下：

```bash
echo 0 > /proc/ax_proc/os_mem/policy   # 设置policy为0
echo 1 > /proc/ax_proc/os_mem/policy  # 设置policy为1
echo 2 > /proc/ax_proc/os_mem/policy  # 设置policy为2
```

## 11. OTA升级使用说明

本章节主要介绍OTA升级功能的使用方法，以便用户在开发过程中了解升级的过程及注意事项。

### 11.1 概要说明

因为车载应用对系统可用性要求极高，OTA 使用 A/B 系统方案，不支持 recovery 方案。

支持功能：

- RSA签名校验，默认使用和安全启动相同的密钥

- HASH校验

- 分区校验，分区不一致时阻止升级

- 软件版本校验

- 压缩

- 分区升级

- 文件升级

- 差分升级

- AB升级

- 升级失败回滚

- 镜像回读校验

- 升级前后执行用户自定义脚本

- 掉电安全

- 本地升级

- 网络升级

#### 11.1.1 AB 系统方案

AB 系统方案，是将原有的系统，增加一份。即flash 上总共有AB 两套系统。两套系统互相升级。OTA 时，若当前运行的是A 系统，则升级B 系统，更新完成后，设置标志，重启切换到B系统。OTA 时，若当前运行的是B 系统，则升级A 系统，升级完成后，设置标志，重启切换到A 系统。

若更新失败，正在运行的系统没有被破坏，系统还能正常运行。若更新完成，切换到新的系统，但更新的系统不可运行，RomCode 配合WDT切换回原来的系统。若更新完成，切换到新的系统，但更新的系统未通过测试，RomCode 配合OTA检查切换回原来的系统。

因为AB更新过程是在完整系统中进行的，更新期间可正常提供服务，用户无感知。最终重启一次即可；开启 AB 同步时需要重启两次。系统的可用性高，停机时间短。

### 11.3.1 AB升级

OTA默认开启AB升级，sw-description-source文件中分为两个大块，A块描述升级SLOT A内容，B块描述升级SLOT B内容，每次OTA只会使用其中一个块。用户修改sw-description-source文件时应该同步修改A和B。

#### 11.3.2 分区升级

sw-description-source默认升级所有系统分区，用户可以自行删减和添加分区来满足不同的升级需求。

#### 11.3.3 压缩

在升级工件描述节点添加compressed = "zlib";可以开启压缩功能，能够减小升级包大小，但会增加升级时间。

```c

compressed = "zlib";
},
```

#### 11.3.4 回读校验

在升级工件描述节点添加readback = "1";可以开启写入镜像后回读镜像校验写入镜像是否发生数据错误，但会增加升级时间。

```c
{

},
```

### 11.5 底层实现

swupdate负责获取镜像和更新镜像，爱芯将各种存储介质读写接口统一，生成了 /dev/link/ota_xxx 设备，swupdate 通过标准的 read/write 命令就可以读写存储介质。AB切换通过RomCode、WDT和安卓abc来控制，AX637系统中的abc已经集成了RomCode控制部分，用户按照标准abc进行使用就能完成切换。AX637 OTA通过安卓bcb在各级boot和AB系统间传递OTA信息。

#### 11.5.1 如何保证更新安全

1. 系统采用AB分区，永远只更新非活动分区，确保外部存储介质至少有一份能够正常运行的镜像。

2. AB切换

  1. RomCode通过复位不丢失掉电丢失寄存器来选择分区，且具备启动失败自动切换分区功能。

  2. RomCode后级采用安卓abc/bcb方案，并添加备份机制，且充分预留坏块，确保更新abc时掉电安全和坏块安全。

3. 存储介质读写

  3. Nand flash按照全生命周期2%坏块率为每个分区充分预留坏块，降低因坏块导致镜像无法写入。

  4. Safety flash读写通过virt mtd设备进行读写，用户空间按照标准mtd设备使用，virt mtd驱动通过RPMSG发送数据与safety flash驱动交互，实际读写操作由safety flash驱动进行。

4. OTA流程

  5. OTA不是原子操作，可能在任意阶段被打断，使用安卓bcb来标记OTA阶段，通过BCB标记检测OTA操作流程，被中断后可以进行处理或者恢复。

  6. 通过硬件WDT来检测镜像无法启动，配合RomCode自动进行AB切换。

  7. 通过OTA升级后检测来排查个别异常设备，确保更新镜像在具体设备上功能完好。

  8. 通过OTA检查来区分OTA状态，回滚更新失败设备。

#### 11.5.2 如何保证信息安全

将各个镜像的SHA256值写入 sw-description，对sw-description 进行RSA签名，然后把sw-description签名文件、sw-description、各个镜像传递给swupdate。

若RSA签名验证通过，说明 sw-description 文件是可信的，也没有被篡改，sw-description 文件中各个镜像的SHA256也是可信的，也没有被篡改。后续的镜像的完整性和可信性可以通过简单的SHA256来校验。

安全启动各级镜像也会进行校验，镜像签名和SHA校验不通过会阻止启动。

安全启动还会校验镜像版本，当前镜像版本小于安全存储版本时会阻止启动。

## 12. BOOTROM 相关介绍

### 12.1 chip mode介绍

图12-1系统启动项选择

![fig 12 1](ax_sdk_usage_00_assets/fig_12_1.png)

![fig 12 1](ax_sdk_usage_00_assets/fig_12_1.png)

由上图可以看出AX637系列芯片支持的启动和下载模式，一般硬件设计前需要和硬件工程师确认strap pin的设置，进而让芯片进入预期的启动或者下载方式。

BootRom中使用的管脚：

- 如果chip mode为Safety_NAND、Safety_NOR模式，OSPI_CSN_0管脚会复用成GPIO6_A06用作CS0，并配置上拉，OSPI_CLK、OSPI_RWDS、OSPI_SIO0-OSPI_SIO7复用成OSPI功能；

- 如果chip mode为Main_NAND、Main_NOR、HyperFlash模式，QSPI_CS0_N管脚会复用成GPIO1_A21用作CS0，并配置上拉，QSPI_CLK、QSPI_SIO0-QSPI_SIO3复用成QSPI功能；

- 如果chip mode为EMMC启动，EMMC_DAT0—EMMC_DAT7会配置成上拉，EMMC_DS配置成下拉，EMMC_CMD配置成上拉，EMMC_CLK配置成不拉，EMMC_PWR_EN配置成gpio function（GPIO5_A04），不做上下拉，EMMC_RESET_N 配置成gpio function（GPIO6_A17），配置成上拉。

如果chip mode为下载模式，若走到SD CARD，SD_DAT0—SD_DAT3，SD_CMD配置成上拉，SD_PWR_EN，SD_CARD_DETECT_N，SD_PWR_SW不做上下拉配置；如果走到UART下载，UART0_TXD，UART0_RXD 会配置成上拉；若走到CAN，CAN6 TX、RX配置成上拉。
