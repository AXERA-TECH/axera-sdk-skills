# AX615 DDR 已知可疑点

本文档用于记录“已有源码事实或版本差异证据，但尚未形成 FAQ 闭环”的可疑点。条目不是缺陷定论，也不能直接作为量产修改依据。

## 1. 条目状态与证据等级

| 状态 | 含义 | 可用于什么结论 |
|---|---|---|
| `待复核` | 仅有初步代码观察，尚未确认实际版本/调用链 | 只能提出下一步取证 |
| `代码事实已确认` | 当前版本源码行为已确认，但现场是否命中未知 | 可说明代码行为，不可断言现场根因 |
| `现场相关性已确认` | 现场证据证明进入该代码路径 | 可形成中等置信度假设 |
| `待原厂确认` | 代码与现场链路成立，但设计意图/规格未知 | 进入 S5 请求原厂确认 |
| `已转 FAQ` | 已有边界、验证和闭环结论 | 应链接 FAQ，避免重复维护 |
| `已排除` | 有证据证明与当前 case 无关 | 保留排除证据和适用范围 |

证据应分为四类：

- **源码事实**：实际版本的 `文件:行号`、调用链、宏值或可搜索代码特征。
- **公开规格依据**：匹配版本的公开芯片手册、颗粒数据手册或公开接口说明。
- **客户证据**：完整日志、配置快照、镜像信息、复现统计和 A/B 对照。
- **待验证假设**：明确写出尚缺什么证据，不能与事实混写。

涉及芯片级内部实现时，只记录“待原厂在受控环境确认”，不得在此文件中复制内部资料内容。

## 3. 可疑点详情

### SUS-001：`chip_type/ddr_type` 可能被硬编码覆盖

**状态**：`待复核`

**源码事实**：实际代码位置和覆盖顺序需在当前源码重新确认。

**潜在影响**：如果来源信息与初始化入口使用的 `ddr_type` 不一致，按类型选择的 PHY pinmux 分支可能与实际颗粒不匹配。

**验证步骤**：

1. 在不改变配置的前提下记录来源信息中的 `ddr_type`。
2. 记录进入 `ax615_ddr_init()` 前后使用的 `ddr_type`。
3. 确认 `ddrphy_pinmux_set()` 实际命中的分支。
4. 对照颗粒料号和板级连接，不仅依据枚举名称判断。

**升级条件**：确认来源信息与初始化实际值不同，且分支变化与现场首个异常有稳定相关性时，进入 S5。

### SUS-002：异常芯片类型回退到默认路径

**状态**：`代码事实已确认`

**源码事实**：当前参考版本存在未知或异常输入进入默认初始化路径的行为，参考 `platform_version_diff.md` 的对应章节。

**潜在影响**：输入未写、读取失败或解码异常时，后续可能表现为合法的默认路径，掩盖环境未闭合问题。

**验证步骤**：记录原始输入、解码结果、最终 `chip_type`、产品丝印和启动日志中的协议/频率。

**边界**：只有最终默认路径发生且产品并非该默认型号，或回退原因未知时，才作为当前 case 的有效嫌疑。

### SUS-003：多个 default 配置链可能同时生效

**状态**：`代码事实已确认`

**源码事实**：当前参考版本中，频率选择、PHY pinmux 选择和 `ax615_ddr_init()` 均存在 default 行为，参考 `platform_version_diff.md` 的对应章节。

**潜在影响**：未知型号可能同时使用默认 DDR3 flow、默认频率/timing 和默认 pinmux；任一项不匹配都可能导致 training 或稳定性问题。

**验证步骤**：为三个选择点分别记录输入值和实际分支，不能只看到 `dram type is DDR3` 就认为配置正确。

### SUS-004：AX615E 配置由编译宏决定

**状态**：`代码事实已确认`

**源码事实**：当前参考配置包含 AX615E 频率和 DDR3/DDR3L 相关编译宏，参考 `platform_version_diff.md` 的对应章节。

**潜在影响**：工作区源码、实际构建头文件和客户板上 BL1 镜像任一不一致，都可能造成频率、协议、电压或 pinmux 判断错误。

**验证步骤**：

1. 确认最终构建实际包含的配置头文件。
2. 记录 BL1 构建时间和校验值。
3. 对照启动日志实际频率、板级 VDDQ 实测和颗粒规格。
4. 确认频率选择宏和 DDR3/DDR3L 选择宏不存在多选或全不选。

**边界**：不得把当前宏值写成所有 AX615E 的硬件规格。

### SUS-005：`ddrmc_train_flow_no_lp.c` 适用范围待确认

**状态**：`已排除`

**源码事实**：文件名包含 `no_lp`，但文件名本身不能证明它只适用于非 LPDDR；当前参考源码中多个协议 flow 可能共享其中的部分训练函数。

**验证步骤**：从 `ddr2_init_flow()`、`ddr3_init_flow()`、`lpddr2_init_flow()` 和 `lpddr3_init_flow()` 分别沿调用链确认 training sequence；记录条件编译和包装函数。

## 5. 维护规则

- 每个可疑点必须有唯一 ID；状态变化时保留原始证据。
- 不能仅凭文件名、注释、变量名或单次实验认定缺陷。
- 若已有稳定复现、机制、适用边界和客户验证方法，应转入 `reference/FAQ.md`。
- 若涉及设计意图、errata、内部实现或量产参数，标记 `待原厂确认` 并使用 `reference/handoff_template.md`。
- 已排除项不要删除；注明排除版本、条件和证据，避免后续重复调查。
