# AX615 DDR FAQ

本文档用于 S3 阶段的常见问题检索、证据整理和客户回复。它只保留公开可复核的源码行为、日志现象、配置核对和低风险验证方法，不包含芯片级内部资料或 PHY 物理实现细节。

## 使用说明

### 这份文档解决什么问题

FAQ 条目用于回答“某个现象通常如何判断、需要什么证据、客户下一步做什么”。它不是芯片手册，也不是未经验证的参数调优清单。

每个条目可包含以下内容：

1. **问题**：客户能观察到的现象，尽量使用原始日志或可复现描述。
2. **适用范围**：芯片型号、DDR 类型、SDK 版本和已知前提。
3. **结论分类**：`设计预期`、`配置或使用方法`、`已知修复` 或 `待验证`。
4. **结论**：一句话回答当前问题，但不能把假设写成事实。
5. **机制/原因**：解释为什么会出现该现象。
6. **客户可验证**：一到三条低风险、可执行的验证步骤。
7. **边界**：哪些现象出现后，当前 FAQ 不再适用。
8. **下一步**：如果无法闭环，应补充什么信息或进入哪一个排查阶段。

### 结论分类怎么选

| 分类 | 什么时候使用 | 最低证据要求 |
|---|---|---|
| 设计预期 | 现象由明确的超时、去抖、状态机或兼容性设计导致 | 源码或公开规格能解释机制，并能给出边界 |
| 配置或使用方法 | 配置、镜像、启动顺序或测试方法不符合要求 | 找到配置读取点、生效链路和日志验证方法 |
| 已知修复 | 有正式问题单、修复记录或可确认的版本差异 | 原始编号、适用版本、代码特征和验证方法齐全 |
| 待验证 | 只有现象或推测，证据尚不足以归类 | 明确缺失信息和下一轮低风险取证 |

### 证据和占位符规则

- 没有实际资料时，使用 `<待填写>`、`<待确认值>` 或 `[待验证]`，不要编造文件行号和修复版本。
- “当前源码宏配置”不等同于“所有硬件的正式规格”。
- 客户提供的硬件分类、源码事实、当前镜像行为和待验证假设必须分开写。
- `training fail`、`BIST fail`、`memtest fail` 只描述现象，不能直接当作根因。
- 每条 FAQ 都要写适用边界；如果源码版本、芯片型号或 DDR 类型不匹配，应回退到 S0/S1/S4，不直接套用条目。

## 常用 FAQ

### FAQ-001：启动或烧录阶段没有日志，或者只有很少量的日志

**适用范围**：所有 AX615 DDR 平台；缺少初始化阶段或首个异常前后的完整日志。

**结论分类**：`待验证`

**结论**：日志不足时不能判断 DDR 是否已经开始初始化。优先确认 BL1 构建是否启用了所需日志、串口配置是否匹配，以及实际烧录的镜像是否为目标版本。

**客户可验证**：

1. 确认 BL1 构建配置中的日志开关、串口端口和波特率。
2. 确认烧录镜像的构建时间、校验值和来源分支。
3. 重新采集从复位到首个异常的完整日志，不要只截取最后一行。

**边界**：即使没有日志，也不能直接把现象归因于 DDR 初始化失败；复位、时钟、串口和镜像不匹配同样可能造成无输出。

**下一步**：补齐可复现条件和完整日志，再进入 FAQ-002 或 FAQ-004。

### FAQ-002：training 全失败，是否就是时序参数问题？

**适用范围**：能够看到 `ddr init start...` 和 training 阶段日志的 AX615 DDR 初始化路径。

**结论分类**：`待验证`

**结论**：不能仅凭 training 结果判定为时序问题。应先确认芯片型号、DDR 类型、实际协议 flow、频率、位宽、Rank、供电和板级条件。

**依据**：

- 指定源码中的 `ax615_ddr_init()` 先选择频率和供电配置，再根据型号选择 `ddr2_init_flow()`、`lpddr2_init_flow()`、`lpddr3_init_flow()` 或 `ddr3_init_flow()`：`/boot/bl1/driver/ddr/ax615_ddr/ddr_init.c:1688-1722`。
- DDR3 training 的阶段顺序和日志位于：`/boot/bl1/driver/ddr/ax615_ddr/ddrmc_train_flow_no_lp.c:534-550`。

**客户可验证**：

1. 记录启动日志中的 `chip_type`、`ddr_type`、协议、实际频率和 training 顺序。
2. 将实际 DDR 颗粒料号、位宽、Rank、容量和电压与源码配置及颗粒数据手册对照。
3. 保持板子、镜像和测试方法不变，只改变一个变量做 A/B 验证。
4. 区分 `pass`、`fail` 和 `timeout`；三者对应的下一步不同。

**边界**：如果型号、协议、频率和颗粒规格已经闭合，且首个异常明确落在某个 training 阶段，才进入该阶段的源码和板级联合分析。

### FAQ-003：降低频率后问题消失，这是否证明频率就是根因？

**适用范围**：存在高频失败、低频成功的可重复 A/B 对照。

**结论分类**：`待验证`

**结论**：这只能证明问题与当前频率配置或频率相关裕量有关，不能单独证明某个 timing、驱动强度、ODT、电源或板级参数就是根因。

**依据**：

- 稳定配置与失败配置的实际日志、频率和镜像差异：`<待填写>`。
- 颗粒数据手册的频率/timing 支持范围：`<待填写>`。
- 源码中的频率选择入口：`/boot/bl1/driver/ddr/ax615_ddr/ddr_init.c:1641-1686`。

**客户可验证**：

1. 保持板子、镜像和测试方法不变，只修改频率。
2. 记录每个频率下的 training 结果、BIST 结果、温度、电压和样本数。
3. 确认频率改变是否同时触发了另一组 timing、pinmux、供电或 training 配置。
4. 至少保留一个稳定配置和一个失败配置，列出两者所有差异。

**边界**：如果只在特定板号、温度或电压下失败，不能把结果简化为“频率太高”；应进入板级、电源和时钟联合取证。

### FAQ-004：客户只提供“启动失败”或“跑一会儿死机”，应该先问什么？

**适用范围**：输入信息不足的所有 DDR 问题。

**结论分类**：`配置或使用方法`

**结论**：先闭合发生阶段和时间线，再决定是否读取源码或开展实验。一次只追问最影响判断的缺项。

**建议收集顺序**：

1. 发生在 BL1 DDR 初始化、U-Boot、Kernel 启动，还是运行时？
2. 首个异常前后各 20～50 行完整日志是什么？
3. 板型、PCB 版本、AX615 具体型号/revision、DDR 颗粒料号和拓扑是什么？
4. DDR 类型、位宽、容量、Rank、目标频率和实际频率是什么？
5. BL1 构建时间、镜像校验值和源码 commit 是什么？
6. 是否与温度、负载、频率、电压或特定板号相关？
7. 稳定配置与失败配置分别是什么，是否只改变了一个变量？

**不应直接做的判断**：

- `training fail` = PHY 坏；
- `memtest fail` = 颗粒坏；
- 偶发启动失败 = timing 参数错；
- 没有日志 = DDR 初始化失败。

**下一步**：按照 S0/S1 先建立环境和时间线，再进入 S2 现象归属。

## FAQ-DDR-005：出现 `dfi polling timeout`，随后训练阶段全部 timeout，应该如何判断？

**适用范围**：AX615 DDR 初始化路径；日志中出现：

```text
dfi polling  timeout ......!
polling read eye training timeout!
polling wrdsk_training done timeout!
polling write eye training done timeout!
```

或者客户描述为“初始化握手超时，后续训练全部 timeout”。

**结论分类**：`待验证`

**结论**：`dfi polling timeout` 发生在 PHY 前置初始化和 training 之前。若后续多个阶段也只有 timeout，而不是明确的 `*_fail`，应优先确认时钟、PHY pinmux、协议/频率配置、前置初始化和训练启动条件，不能直接归因于某一个读写 timing 参数。

**机制/原因**：

- `ddr3_ddrphy_pre_init()` 完成 DDR3 PHY 前置配置后调用 `ddrmc_phy_init()`：`/boot/bl1/driver/ddr/ax615_ddr/ddr_init.c:1021-1082`。
- `ddrmc_phy_init()` 执行有限轮询；若等待未完成，会打印 `dfi polling  timeout ......!`，随后返回当前 flow：`/boot/bl1/driver/ddr/ax615_ddr/ddr_init.c:922-936`。
- 当前源码的 DDR3 flow 在前置初始化之后继续进入 training：`/boot/bl1/driver/ddr/ax615_ddr/ddr_init.c:1326-1333`。

**待验证假设**：

- DDR 时钟没有按实际选择结果生效；
- PHY pinmux、DDR 类型、位宽或 Rank 与板级设计不一致；
- 协议、频率或型号专用配置不匹配；
- 前置初始化未完成，但后续 flow 仍继续执行；
- 电源、复位、时钟或板级连接异常。

这些只是待验证假设，不能仅凭连续 timeout 确认具体根因。

**客户可验证**：

1. 确认日志中的实际 DDR 频率与 `ddr_freqs_get()` 的选择结果一致：`ddr_init.c:1641-1686`。
2. 确认实际进入的协议 flow，不要只依据 `dram type is DDR3` 一行日志。
3. 核对 `ddr3_ddrphy_pre_init()` 是否命中了与型号、频率和颗粒相符的配置分支。
4. 保存 timeout 前后的完整日志和构建信息；不要在没有板级和颗粒依据时直接修改频率、电压、ODT 或驱动强度。

**边界**：

- 如果初始化握手不再 timeout，但训练仍 timeout，应转入具体 training 阶段分析。
- `dfi polling timeout` 不等同于 PHY 损坏，也不等同于时序参数错误。

**下一步**：请补充 `chip_type`、`ddr_type`、实际协议 flow、实际频率、DDR 颗粒料号、位宽、Rank、构建版本以及 timeout 前后完整日志。

## FAQ-DDR-006：读训练和写训练都失败，应该如何判断？

**适用范围**：DDR 初始化已进入 training，日志中出现读眼训练失败、写 deskew 失败或写眼训练失败，例如：

```text
read eye training fail!
write deskew training fail!
write eye training fail !
```

**结论分类**：`待验证`

**结论**：读写训练都失败，说明当前配置下读写校准都没有获得有效结果。应优先检查共同前置条件，而不是同时修改读 timing 和写 timing。

**依据**：

- DDR3 training 顺序为公共前置配置、读路径训练、写路径前置配置、写 deskew 和写 eye：`/boot/bl1/driver/ddr/ax615_ddr/ddrmc_train_flow_no_lp.c:534-550`。
- 读眼训练、写 deskew 和写 eye 的独立函数及日志位于：`ddrmc_train_flow_no_lp.c:284-330`、`385-416`、`449-483`。

**优先检查的共同前置条件**：

- DDR 协议和实际型号是否匹配；
- `ddr_types` 对应的位宽、Rank、容量是否与颗粒一致；
- 频率和 timing index 是否对应当前配置；
- PHY pinmux 和板级连接是否匹配；
- PHY 前置初始化是否完成；
- VDD/VDDQ 是否满足颗粒规格；
- training pattern、byte enable 和测试方法是否与位宽一致。

**客户可验证**：

1. 按日志顺序记录每个阶段是 `pass`、`fail` 还是 `timeout`。
2. 确认 x16/x32、Rank、容量和协议配置一致，不要只看最终打印的协议名称。
3. 先固定 flow、位宽、Rank 和电源，只改变一个变量进行 A/B 验证。
4. 如需进一步分析，提供读写训练前后的完整日志、源码版本和 training 输出结果，不要复制受控低级资料。

**边界**：

- 读写训练都 fail 不足以证明 DDR 颗粒损坏。
- 如果所有阶段都是 timeout，应优先分析训练启动和前置初始化，而不是先调整 eye 参数。
- 如果只有某一个 byte、Rank、温度或板号异常，应记录局部相关性，不能直接归为全局 timing 错误。

**下一步**：补充训练阶段顺序、首个异常、实际 flow、位宽、Rank、频率、DDR 料号和稳定/失败单变量对照。

## FAQ-DDR-007：读训练通过，但写训练失败，应该如何判断？

**适用范围**：读眼训练通过，但写 deskew 或写眼训练失败，例如：

```text
read eye training pass!
write deskew training fail!
```

或：

```text
read eye training pass!
write eye training fail !
```

**结论分类**：`待验证`

**结论**：读训练通过、写训练失败，只能说明当前测试中读路径得到过可用结果，不能推出写路径、输出时序、板级连接和供电都正常。应重点分析写训练阶段及其共同前置条件。

**机制/原因**：

当前 DDR3 training 中，读路径和写路径由不同函数处理：

```text
读路径：
ddr3_ddr4_train_rd_pre_set()
ddr3_train_rdeye_duty_cycle()

写路径：
ddr3_ddr4_train_wr_pre_set()
ddr3_ddr4_train_wrdsk()
ddr3_ddr4_wreye_train_flow()
```

依据：`/boot/bl1/driver/ddr/ax615_ddr/ddrmc_train_flow_no_lp.c:534-550`。

写训练前还会根据实际位宽准备不同测试数据和窗口配置：`ddrmc_train_flow_no_lp.c:418-438`。

**客户可验证**：

1. 区分是写 deskew 失败、写 eye 失败，还是二者都是 timeout。
2. 核对实际 x16/x32、Rank、频率、协议和颗粒 speed bin。
3. 核对 `ddr3_ddrphy_pre_init()` 是否命中了正确型号和频率分支：`ddr_init.c:1021-1082`。
4. 保持频率、颗粒、电压和板子不变，只改变一个写路径相关变量进行验证。
5. 保存失败阶段前后的日志、训练输出和稳定对照组。

**边界**：

- 读训练通过不代表写路径、输出时序或板级信号完整性一定正常。
- 写训练失败不等同于 DDR 颗粒损坏。
- 如果写训练是 timeout，应优先分析启动条件和前置状态；如果明确是 fail，再分析写窗口和物理裕量。

**下一步**：提供读写阶段结果、首个失败点、实际 x16/x32、Rank、频率、DDR 料号、板级条件和单变量对照。

## FAQ-DDR-008：读写训练都通过，但 BIST 全部失败，应该如何判断？

**适用范围**：training 日志显示读写阶段通过，但后续所有 BIST case 都失败，例如：

```text
BIST_ALLWRC LFSR_DATA_PATTERN---->bist fail
BIST_ALLWRC USER_DATA_PATTERN---->bist fail
BIST_ALLWRC SIPI_DATA_PATTERN---->bist fail
BIST_ONEWRC LFSR_DATA_PATTERN---->bist fail
BIST_ONEWRC USER_DATA_PATTERN---->bist fail
BIST_ONEWRC SIPI_DATA_PATTERN---->bist fail
```

**结论分类**：`待验证`

**结论**：training 通过只说明 training 阶段按当前源码的判据得到通过结果。若所有 BIST case 都失败，应先确认 BIST 是否真正完成、测试参数是否与实际位宽和内存范围一致、测试是否覆盖了有效内存，以及 training 后的控制流程是否正确，不能直接把 BIST 全 fail 归因于颗粒损坏。

**依据**：

- `bist_init()`、`bist_test()`、`dram_bist_test()` 和 `ddr_bist_proc()` 位于：`/boot/bl1/driver/ddr/ax615_ddr/ddr_init.c:1116-1303`。
- `ax615_ddr_init()` 在协议 flow 完成后调用 `ddr_env_bist_scan()`：`ddr_init.c:1688-1722`。

**优先排查的共用项**：

- 测试是否完成，还是一直等待完成条件；
- BIST mode、pattern、burst length、data size 和 data width 是否被正确选择；
- 起始地址和测试范围是否落在有效 DDR 区域；
- 是否覆盖启动代码、栈、保留区或正在使用的内存；
- 失败位置、失败次数、期望数据和实际数据是否稳定；
- BIST 是否在其他测试或 eye scan 之后运行，是否存在遗留配置影响；
- 测试前后的 training 和 controller 状态是否一致。

**客户可验证**：

1. 先确认每个 case 是 `pass`、`bist fail` 还是没有完成；没有完成不能按数据错误处理。
2. 只运行一个最小 BIST case，固定一个 pattern、一个 burst length、一个 data size、一个有效起始地址和较小测试范围。
3. 保存该 case 的完整输出，包括失败位置、失败次数、期望数据和实际数据。
4. 确认测试范围没有覆盖启动代码、栈、保留区或在线使用的内存。
5. 不要因为 BIST 全 fail 就直接更换颗粒或修改 timing。

**边界**：只有在测试已完成、参数和范围已确认、失败数据稳定且能重复复现后，才适合进一步分析数据通路、电源、信号完整性或颗粒兼容性。

**下一步**：提供 BIST 结果矩阵、最小 case 输出、实际内存映射、测试范围、失败位置/数据、源码版本和稳定对照。

## FAQ-DDR-009：读写训练都通过，但 BIST 只有部分 case 失败，应该如何判断？

**适用范围**：training 通过，BIST 仅有部分 pattern、burst length、data size、读写模式或地址区间失败。

**结论分类**：`待验证`

**结论**：部分 BIST 失败更适合做模式、位宽、地址、byte lane、读写方向和数据内容的相关性分析。它可能提示边界裕量、局部数据通路、特定测试组合或测试参数问题，但不能仅凭某一个 pattern 失败直接判定颗粒或板级信号完整性故障。

**机制/原因**：

当前 `ddr_bist_proc()` 会遍历多个 burst length、data size、读写模式和数据 pattern：`/boot/bl1/driver/ddr/ax615_ddr/ddr_init.c:1285-1303`。

**客户可验证**：

1. 制作 BIST 结果矩阵：

   | Mode | Pattern | Data size | 结果 | 失败位置 | 失败次数 |
   |---|---|---:|---|---|---:|
   | `<待填写>` | `<LFSR/USER/SIPI>` | `<待填写>` | `<pass/fail>` | `<待填写>` | `<待填写>` |

2. 保持其他条件不变，只改变一个变量，建议顺序为：

   ```text
   先固定地址、data size
   → 只切换 pattern
   → 只切换读写模式
   → 只切换 data size
   ```

3. 每个失败 case 保存完整输出，并对比失败位置、失败次数、期望数据和实际数据。
4. 检查失败是否集中在相同地址、byte、bit、Rank、温度或板号。
5. 确认每个 case 的参数确实被当前镜像使用，而不是日志标签或旧配置残留。

**边界**：

- 部分 BIST 失败不自动等于“DDR 稳定性差”或“颗粒损坏”。
- 如果失败只在特定 mode、pattern、burst 或 data size 出现，必须先确认该参数已正确生效。
- 如果失败位置和模式均不稳定，应优先检查测试流程、完成条件、日志完整性和测试范围。
- 如果失败稳定集中在相同地址、byte 或 bit，并且最小 case 也可复现，才升级分析地址映射、DQ/DQS、板级、电源和颗粒规格。

**下一步**：提供完整 BIST 结果矩阵、失败 case 与稳定 case 的单变量对照、实际内存范围、温度/电压、板型和镜像版本。

遇到 DFI、training 或 BIST 问题时，优先保存以下公开信息，并注明采集时刻：

### 初始化和 training

- `chip_type`、`ddr_type` 和实际协议 flow；
- 目标频率与启动日志中的实际频率；

- 测试工具或调用入口；
- mode、pattern、burst length、data size 和位宽配置；
- 起始地址、测试范围、循环次数和时长；
- 是否可能覆盖有效内存；
- 失败位置、失败次数、期望数据和实际数据；

- AX615 具体型号/revision、板型和 PCB 版本；
- DDR 颗粒完整料号、协议、位宽、Rank 和容量；

- 稳定配置与失败配置的单变量差异。
